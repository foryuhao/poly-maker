# 101笔目标、提交额度与观察窗口

日期：2026-11-11。状态：`LOGICAL_CAPACITY_REVIEW_NOT_FREQUENCY_MEASUREMENT`。本文只推导M12–M22的COMMON额度如何约束成交数，不启动测试或统计实际行情，也不改变任何SOP/执行参数。M1–M11按各自冻结执行版本另行核对，不能自动套用本文额度。

## 1. 计数单位是实际订单，不是root或信号数

对一个冻结策略版本，COMMON规定每个`(market,token)`最多一次实际提交，拒单也消耗该次额度；同一证据root也最多一次。新root、新fact ID或重新配对都不会恢复该市场/token已经消耗的额度。

令G为预先定义观察范围内的市场/token组。对每组，提交、订单生效、至少一次确认成交、已知官方结算分别最多贡献一笔。若各阶段来自同一订单全集和冻结口径，则：

`N_settled <= N_filled <= N_live <= N_submitted <= |G|`。

费用未知时，已确认成交且官方结果已知的订单仍可报告为“已结算订单”；但其净PnL尚不能被当成已知，不能据此宣布全部经济目标达成。应另报经济账可完整核对的订单数，而不是把缺费用填0，或把已结算身份与净收益可用性混成一个字段。

候选root数量可以远大于|G|，因此signals多不代表可达到101笔。部分成交合并到原order_id；两个模拟模型、两个SOP版本或不同策略不能相加凑单一策略的门槛。只有策略版本、执行模型、窗口和区间身份一致的订单才能组成该次验收集合。

## 2. 名义上限与真正可用机会

**条件算例**：若24h起止与五分钟市场边界对齐，期间恰有288个完整且在合同范围内的市场，每场两个token，每个token都允许一笔，则名义提交上限为`288*2=576`。至少101笔已结算成交占此上限`101/576≈17.53%`。

这不是实际频次估计。它没有证明288个市场的覆盖、区间内档位、足够资金、合法Maker、订单被接受、有效期内排到或结算账齐全。若某冻结政策只允许每场一个方向/一笔，总上限还会更低；不能借两token理论上限评价实际上禁止双侧提交的政策。

真正决定可行性的，是具有可提交机会的独立组及其执行转化：

| 同一冻结政策下具有可提交机会的独立组数 | 要得到101笔所需的最终结算成交比例 | 含义 |
|---:|---:|---|
| 576 | 约17.53% | 只在上述名义机会全部可用的假设下 |
| 288 | 约35.07% | 仍未说明是否有足够有效期内成交 |
| 200 | 50.50% | 方向条件不能替代后续排队与结算 |
| 120 | 约84.17% | 余下执行阶段可损失的机会已很少 |
| 100或更少 | 不可能达到101笔 | 即使每组都成交并结算也不足 |

表中是定义推导，不是对任一M信号的预测。`具有可提交机会`也不是事后挑出最终会成交的组：应由因果时点上的准入条件定义；实际候选、发送、接受和成交损失分别记录。资金/并发限制可能使组间耦合，这些比例不能当作相互独立事件概率相乘。

如果先前拒单或其他已经发生的提交消耗额度，即使后来出现条件更好的候选，也不能把它计入本版本尚可执行的机会。不能通过恢复额度或改名root，让不够频次的版本看起来达标；若将来改变额度，那是明确的新执行版本。

## 3. 价格区间的两个角色必须标明

目标主区间为预先选定的0.20–0.80，但区间用于**下单前准入过滤**，还是只用于**事后报告分层**，会影响同一策略的额度消耗与成交集合。本页不替测试模块切换这项政策，也不将SOP中的价格分层字段暗改成新方向信号；收到结果时必须能识别实际选择。

规则例：同一市场/token先有P=0.15的候选，后来有P=0.50的候选。

- 若冻结政策在下单前过滤0.20–0.80，第一候选不会产生提交；在其他条件仍满足时，后来候选可能使用尚未消耗的额度。
- 若政策允许全价位提交、最后仅报告0.20–0.80，第一候选一旦实际提交，即使被拒也占额度；后来0.50的候选不能补下。报告中看不到0.15订单，不代表它没有影响区间内机会。

两者都是不同的执行/评价设计，不能只看到最终价格列相同就混池。区间外订单若真实发生，完整账户经济暴露仍保留；主区间结果与全价位结果分别报告，不把区间外亏损从整个账户账本删掉。

同样，按信号锚价筛选与按实际成交价筛选也须预先标识。合法原锚Maker不允许临时改价后仍挂原信号名；实际价若与锚价不同，按冻结模型解释并单列，不能选择对结果更有利的一列。

## 4. 24小时观察与最终结算不是一个时点

建议测试模块预先固定准入/提交窗口`[t0,t1)`、其中t1-t0=24h，并明确市场纳入规则、价格区间角色、版本hash和评价截至时刻。完整五分钟市场对齐可减少边界歧义，但本页不替已经冻结的实验更改起止或市场全集。

若窗口不对齐市场边界、包含前一场的尾部或最后一场的开头，不能无条件套用288/576。实际G须按已冻结的市场元数据与纳入规则确定；不从文件个数或计划市场数推定覆盖完成。

窗口结束后，属于该次提交集合的订单仍需核对取消、迟到成交及官方结算。可以等待这些既有订单的完整结果；这不授权窗口外新增入场或给旧信号续期，也不能把结算等待时间算成额外信号观察窗口。冻结评价截至时仍未结算或经济信息未知的，明确报告状态，不能补零凑101笔。

部分成交跨过窗口边界，按预先确定的订单归属保留完整经济账，不把后来不利的一段裁掉。若实验选择首次成交时间作为纳入窗口，属于另一种冻结口径，应与提交窗口方式分开，不能看完结果后更换。比较时的剩余时间标签另见[Maker成交筛选审查](MAKER_SELECTION_REVIEW.md)。

连续24h不等于从多个日期挑满288场；中间质量不足也不能删除后把两端时间拼接成“全程可用”。输入质量、总覆盖与有效样本各自报告，不能靠延长或替换市场补出原窗口已达标的说法。

## 5. 对当前新信号的研究影响

- M13/M15/M22沿用旧支撑或历史组件期限，可能确认后已没有400ms提交余量；应计为候选到准入的损失，不改称成交失败。
- M17/M20等待成交后数量复核会消耗原寿命；完成复核不能重给3秒。排不到与没有准入要分开。
- M21的第二轮平稳基线、M20/M22的多档连续结构可能在形成阶段结束root；多个失败root并不增加市场/token提交额度，也不能仅按观察窗口短就推断日成交多。

这些是SOP中的潜在阶段约束，不是测得的发生频率。没有按冻结版本反馈的阶段分母前，不能据此把哪一项排成更赚钱，也不为了101笔放宽质量、延长证据或拆分订单。

本轮仅增加交接说明，研究顺序M12–M22不变。建议有限摘要带上`strategy_version, execution_version, window_membership_rule, price_band_role, price_filter_field, market_token_groups, groups_with_admissible_opportunity, submitted_orders, rejected_orders, live_orders, filled_orders, settled_orders, economic_ledger_complete_orders, quota_consumed_outside_band, pending_or_unknown_orders`。这些是未来反馈字段，不要求本任务生成数据或让测试模块增加大量日志。
