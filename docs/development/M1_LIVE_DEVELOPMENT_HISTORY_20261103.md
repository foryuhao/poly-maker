# M1 实盘策略开发注意事项

日期：2026 年 11 月 3 日，北京时间。

M1 根据同一买档的反复补给 RF 与主动卖压衰竭 AP→EX 授权 Maker 买入，成交部分持有至结算。本文同时保留交易需求和实现历史，不能将离线测试通过视为上线验收完成。当前阶段已退回公共行情虚拟执行：真实下单入口关闭，实盘恢复须另外获得用户确认。

当前工作范围只优化 M1；其他策略不再作为后续执行或验收目标。

## 2026-11-03：M1 移除主动 Merge

按用户要求，`M1Market.run` 已移除 Merge 调用及 MERGING 阶段，M1 也不再创建新的 Merge 意图。旧通用入口在 M1 模式下同样跳过 Merge。T300 通过订单关闭核对后，记录 `settlement_policy=PLATFORM_AUTO_SETTLEMENT` 与实际剩余持仓；持仓非零时状态为 `AWAITING_PLATFORM_SETTLEMENT`，不会预记回款或释放尚未到账的账户资金。是否到账继续以平台真实余额/持仓读数为准。

历史 Merge 事件只读保留：已确认回执用于恢复正确的持仓数量；旧事务结果不明仍要求先核对原收据，禁止遗忘旧风险或重发历史链上操作。这里不再有新的合并、重试或补提交流程。实盘入口的禁用状态保持不变；虚拟记录继续按官方最终胜负计算其明确标记的假设收益。

## 当前验收门槛：公共行情、虚拟开仓、官方结算

`uv run polymaker m1-run` 当前只运行虚拟适配器。公共 HTTP 传输只允许官方 CLOB／Gamma 的 HTTPS GET；订单 SDK 在最终原生 POST 边界替换为本地模拟回报，不发送真实 POST/DELETE。服务不读取 `.env`、用户钱包和账户配置，签名使用临时生成的无资金测试身份。旧实盘命令及旧运行函数仍阻止真实网络启动，已有账户风险记录不清除。

基线开仓沿用冻结 cal-16 信号，窗口 `[T15,T240)`、价格 `[0.01,0.19]`。按用户最新要求，每笔目标支出 1 USDC，股数为 `1 / 信号价格` 向上取整至一位小数，实际支出允许略高于 1 USDC；最小 5 股并满足市场最小数量。每场最多 5 笔成功指令，跳过的信号不占成功名额，重启后继续从持久化记录计数。每个独立 RF／EX 只记一次。成功仅表示虚拟执行回报已持久化；按指令价足额成交并持有至官方结算计算收益，不证明真实 Maker 能成交。历史记录不重新计算；新版本重启之后采用共享提交前链路，虚拟流动性不写入公共盘口。

## 2026-11-03：共享 POST 前执行链路

虚拟与待启用实盘均直接使用 `m1_live.M1Market`，包括 `advance` 调度、信号收集与去重、入场时间/盘口/账户时效检查、实际金额预留、报价、重试、签名准备以及发送前最终检查。删除了虚拟运行器原来的独立 `VirtualPolicy` 入场逻辑。修改共享类会同时影响两种模式，不再分别维护交易规则。

两种模式还直接使用同一个 `M1Ledger`、`ExecutionGateway.prepare/send_prepared`、SDK `create_order/post_orders` 和 `ExecutionClobClient._post`。只有完成签名经济值、Maker/GTC、请求体哈希及最终准入检查之后的 `_native_order_post` 才分流：实盘适配器向官方发送；虚拟适配器记录可恢复的本地满额成交事实并返回模拟 ACK。公共网络仍为 GET-only，虚拟签名客户端禁止网络 GET/DELETE，不加载用户密钥。实盘入口仍禁用。

账户与环境输入也由适配器区分：实盘使用实际账户快照，虚拟明确使用每场 20 USDC 的模型账户，随后经过同一个账户新鲜度、库存对账、可用资金及额度检查函数；两者没有被宣称为同一个真实账户。虚拟设置记录 `prepost_engine=M1Market`、模型账户来源和临时签名来源。相同逻辑不保证不同账户、行情时序和成交输入下做出相同决策。

当前两种模式均按一位小数向上取整，并以合法实际目标金额预留资金：例如 0.19 × 5.3 = 1.007 USDC。最多 5 个已接受或发送结果未定/在途任务；明确拒绝可为原任务重新准入，不增加信号分母。重试价格改变时，原信号目标不改写，但重新检查、预留新的实际金额，避免 0.19→0.18 时目标支出从 1.007 增至 1.008 而漏记风险。每场 20 USDC 的总风险上限继续保留。

虚拟提交前风险状态独立保存在 `research_outputs/m1_virtual/prepost/<slug>.sqlite3`，使用与实盘相同的事务账本。已写入模拟回报但尚未输出报告时，重启从事实恢复，不再提交；旧虚拟指令原样保留并占用本场剩余笔数及金额。新的实盘账本策略版本与旧硬预算账本不兼容，遇到旧风险账本会明确阻断恢复，不能静默改写旧订单金额或清除其风险。

验证包含实盘 SDK 配合离线网络回报与虚拟适配器的成对测试：相同输入得到相同已签名买卖方向、价格/份额经济值和 Maker/GTC；修改共享 guard 同时阻止两种模式；签名期间信号过期、余额不足、5 笔限制、重试取整补占款、被篡改的未知风险及回报写盘中断都覆盖。357 项相关回归通过，包括既有信号、M1 生命周期及共享 SDK 的 CA/Taker 路径；静态检查通过。未进行真实下单，也未把此前 07:20–08:20 的验收数据重标为本次改造后的验收。后台需以新源码重启，后续连续观察按新版本单独开始。

逐场 SQLite 记录信号组件、机会、YES／NO、价格、股数、虚拟成功、异常和官方结算证据；输出 `research_outputs/m1_virtual/latest.json` 与 `report.md`。未有官方最终胜负时 PnL 为待定；完整但无指令的场次在官方结算后计零。信号成功记录与真实 POST／真实成交严格分开。

后台必须连续运行 1–2 小时，覆盖至少连续 12 场完整的 T15–T240 观察与官方结算报告。晚加入、断流、超时、超出容差的源时序或处理积压、进程中断及代码／参数部署均保留异常记录并重置连续计数。轻微乱序继续按 CA 的 20ms 忽略规则，不倒序回填。问题修复后重新连续运行。控制注入的读超时、HTTP 400、公共 WS 断开、进程重启也不混入正常验收样本。

达到 12 场只标记等待用户确认；用户核对每场时间线和模拟 PnL 并确认后才结束本阶段。不会自动恢复真实 POST。Dashboard 修复仍按用户要求延后。

验收调试发现异常帧逐条落库、心跳在主循环重整全部时间线会反过来增加处理积压。现使用批量观察日志、限频诊断和独立只读 SQLite 事务。最初移到线程后仍与行情处理共享 Python 执行资源，实测一次报告消耗约 580ms CPU，因此进一步移到独立低优先级进程，并为场次时间线加索引；大型报告不传回行情进程。拒绝总数保留在检测器计数中，诊断限频不改变任何信号判定。定时官方时钟 GET 在后台执行，避免常规网络等待挡住短 RF／EX 重叠。时间线按实际墙钟与事件序号排序；虚拟成功时间为指令已写库之后。

实测定位到与 43ms 行情处理停顿重合的整代内存回收。当前只在本场订阅前和 T240 关闭公共连接后集中回收，信号处理期间延迟自动循环回收，引用计数仍工作；所有退出路径恢复原开关。持续记录循环延迟、具体处理操作耗时与 CPU 耗时、积压帧数、源时序、回收暂停和 WS 重连原因。超限后仍按原信号门槛失效，不放宽参数。

另一处已修复的误计数：旧场次结算从列表接口回退，被误记到当前场次。结算现复用官方精确 slug 明细路径，旧结果查询重试只记录在原场次，不影响当前行情健康计数；结果未确认时持续保留待结算。

当前虚拟专项 29 项通过，包括原生写请求被传输层拦截、官方路由回退、持久化去重与预算、官方结算身份校验、待定 PnL、12 场及用户门槛、进程恢复、报告进程与行情进程的隔离、回收开关恢复，以及慢时钟读取不挡信号、读超时／连接重置／HTTP 400 恢复后继续生成指令。此前相关信号、公共观察器、旧执行器及结算回归 206 项通过。离线结果不能替代连续场次验收。

已有实测上游源数据迟到 0.5–1.7 秒、但本地处理仅约 0.1–0.4ms 的例子；程序按既有门槛拒绝并重建证据，不放宽冻结参数。用户现已明确确认：自动恢复且记录完整，可以计入正常场次。07:20–08:20 的 12 场据此可计为连续正常完整报告；此为口径确认，不是最终阶段验收。静态验收报告已更新，原始告警保留；实时旧“零告警”计数字段尚待同步新口径，真实 POST 继续关闭。

用户已授权开发独立的 `uv run polymaker m1-run` 入口；后续以 M1 测试为主，CA 保留作对照。现有 300 场采样已结束，研究源码和参数保留，开发前已在该研究目录的 `frozen-runtime/manifest.json` 验证并归档源码。旧实现说明中的 T100、单笔 5 美金、单张活动订单、随 RF／EX 到期撤单属于旧版行为，不能作为新版默认规则。

## 已确认的交易规则

| 项目 | 后续实盘口径 |
| --- | --- |
| 方向 | YES、NO 分别识别 RF_BID 与 EX_SELL；库存仅作额度与核对输入，不产生交易动机 |
| 新单窗口 | `[T15, T240)`，以市场官方时间和本地单调时钟换算 |
| 首轮验证价格 | RF 挂单档位价格在 `[0.01, 0.19]`，包含两端；该范围是本次验证条件 |
| 下单方式 | Buy Only、Post-only Maker，在信号记录的 RF 承接档位挂单；不自动改到新的 Best bid，不转 Taker |
| 单笔目标 | 目标 1 USDC，股数向上取整至一位小数；实际支出允许略超 1，至少 5 股且满足市场最小份数 |
| 单场额度 | 最多 5 笔成功指令；在途及 UNKNOWN 先占用名额；实际支出＋未决占款不超过 20 USDC，不用库存、Merge 或结算回款抵扣累计支出 |
| 订单存续 | 已接受订单不因 RF／EX 消失而撤；已接受或部分成交的订单不改价、不补单，继续等到 T300 |
| 收尾 | T240 停新单，挂至 T300；剩余订单关闭并核对后保留全部残仓，交由平台自动结算；不执行 Merge |
| 手动退出 | Ctrl+C 停止新单，等待实际发送任务返回并保存事实，保留挂单；下次 M1 按已签名 ID 接管 |
| 账户 | 沿用 CA 账户，分时运行，共用账户锁；CA 不得撤销未完成的新版 M1 留单 |
| 机会去重 | 同一独立 RF 与 AP→EX 过程只授权一笔 1 USDC 买入任务；发送失败可为原任务重试，不新增信号分母和预算 |
| 重试 | 确认未接受后可重试至 T240；重试价为 `min(原信号价, 当前 Best bid)`，按新价向上取整到一位小数并核对实际占款；始终 Buy、Post-only、GTC |
| 自有盘口 | 用户确认自有挂单也是真实盘口，全部进入下一次信号判断；不剔除、不屏蔽已挂过单的档位 |
| 并发 | 额度足够且有新的独立机会就可继续挂单，不等待前一张关闭；当前最多 5 个成功或在途任务，POST 请求串行、订单可并存 |

价格用于识别档位、报价合法性、数量换算及上述验证范围。方向判断和持仓退出不加入价格涨跌、浮盈止盈、均价修复或库存配平触发。

当前数量换算共用 `baseline_quantity`：0.19 的目标为 5.3 shares、支出 1.007 USDC；0.01 的目标为 100.0 shares、支出 1 USDC，同时服从市场元数据中的最小下单份数。`budget_quantity` 保留给历史研究和其他旧调用，不再决定两条 M1 执行路径的数量。

## 信号有效期与订单寿命

RF／EX 有效重叠用于授权新的买入任务和首次原生 POST，不作为已接受订单的撤单期限。签名和排队不能刷新原信号时间。用户后续确认：首次 POST 明确失败后，原任务的重试授权延续到 T240，即使 RF／EX 已到期；不把旧证据伪装成新信号。

需要区分原生 POST 尚未开始、明确拒绝和回执不明。首次原生 POST 前证据过期，准备结果失效；已有明确失败的任务可按原价或更低 Best bid 重试。每次保存签名 ID、报价和失败证据，任务总风险仍为 1 USDC。超时／5xx／重复订单错误保留 UNKNOWN，先按原签名 ID 查询，不改签一个可能重复成交的新单。425／429 等明确拒绝按退避重试，参考 [Polymarket 错误码](https://docs.polymarket.com/resources/error-codes)。

采样使用的 `cal-16 / m1-hold-v2` 与配置类默认值不同：RF 为两轮、每轮 500ms，RF 保留 8 秒，EX 确认后保留 750ms。其余门槛从冻结配置读取，不凭旧文档重建参数。该配置中的 400ms POST 预算和 50ms 最低存续预算属于旧的严格挂单模拟，须与新版提交准入、订单存续分别审查，不能原样绑定到长期挂单。

冻结参数来源：`research_outputs/m1_isolated/studies/m1-paper-20261101T125004Z/frozen-config.toml`。

## 现有模块的复用与改造

| 模块 | 复用内容 | 新版需要调整的边界 |
| --- | --- | --- |
| `rdp_sm_marketdata.py`、`rdp_sm_m1_signal.py` | 公共行情、RF/AP/EX 证据与时序检查、互补成交视图 | 持续识别独立机会，自有真实挂单按整体公共盘口纳入，不扣减也不屏蔽 |
| `rdp_sm_m1.py` | 现有 M1 策略入口、档位与金额换算 | 解除对 `BANormalController` 的继承；独立单引擎策略状态，不复用 NORMAL／REPAIR 的交易意图 |
| `rdp_sm_lifecycle.py`、`rdp_sm_loop.py` | 签名准备、持久化意图、原生提交、关闭核对的公共操作 | 将准备、活动订单、回调及截止状态按订单隔离；健康活动订单不能阻止下一独立机会 |
| `rdp_sm_execution.py`、执行 Gateway、StateStore | 签名身份、订单 ID、成交去重与核对、恢复、实际金额账本 | 单独维护 M1 累计支出与占款；完整关闭证明用于最终收尾，不作为所有新单都必须等待的全局门槛 |
| `rdp_sm_cached_reads.py` | 同一账户快照、订单与成交回报核对、写操作后的读取边界 | 保持缓存的新鲜度和完整性要求，逐订单跟踪未决事实 |
| `rdp_sm_merge.py` | 历史合并模块 | M1 不调用；历史已确认回执只用于只读持仓核对，未知旧事务不自动清除或重发 |
| RiskJournal、CAWriter、现有日志与 Dashboard | 恢复日志、有界异步写盘、心跳及展示 | 补充 M1 信号、订单、占款和信号达成率，避免依赖研究日志替代交易风险账本 |

旧 `own_active` 会在活动订单期间暂停识别并清理证据。用户明确要求把自有挂单计入真实整体盘口，因此新版不启用该开关，不扣减自有数量，也不屏蔽同档后续信号。机会仍以新的独立 RF 与 AP→EX 去重；重试仍归入原任务，不能因多次 HTTP 发送新增信号。

SDK 客户端目前有共享的提交回调、`batch_attempts` 和批次标识。并发存续订单不等于直接并发调用整套旧生命周期。可复用公共写操作的串行保护，但必须保证每张订单的回调、占款、成交和核对状态不串用。

当前 `committed()` 会扣除 `merged_cost`，与 M1 累计支出不恢复的口径存在差异；实现时须为 M1 单独处理，不能只复用方法名。配置类中的 `start_sec=100`、`order_budget_usdc=5` 和旧单订单准入也需要显式迁移，不能仅修改配置文件。

## 真实交易容差

| 情况 | 开发规则 |
| --- | --- |
| 轻微乱序 | 参照当前 CA 配置的 20ms：忽略旧事件，不倒序补算、不刷新盘口、不延长信号期限；同时间戳沿接收顺序处理 |
| 被忽略的成交 | 保留其已知方向与数量的保守边界，不用于证明 RF／AP；不能把漏掉的 SELL 当零，进而制造 EX |
| 延迟与积压 | 源数据年龄、接收年龄、处理积压分别判断和记录；CA 当前配置的参考值为源年龄 500ms、盘口接收年龄 200ms |
| M1 处理期限 | 当前另有 200ms 积压阈值、EX 封口后的 50ms 处理余量；须显式配置和验证，不能用乱序容差替代 |
| 数值核对 | 使用 Decimal 和实际成交经济值；订单身份、token、方向、价格档位和机会归属保持严格一致 |
| 价格差异 | 共享代码的绝对 0.01 价格核对容差，不是允许多付 0.01 的报价权限。低价 M1 须单独审查，签名金额与资金上限不能因此放宽 |
| 接近成交完毕 | 共享 `MATCHED` 剩余不超过 0.1 share 的规则可用于终态核对，仍须核对完整成交证据；不补记未成交数量，也不把达成率记成 100% |
| 迟到和部分回报 | 实际发生的成交均按订单归属入账；撤单 ACK、订单暂时消失或一次空查询不能作为释放占款的充分证明 |
| UNKNOWN | 保留签名 ID、原机会去重状态和全部可能占款，继续查询；不能当成明确拒单去改签新 ID |
| 索引滞后 | 复用账户、订单、成交和现金的交叉核对。现有短期库存宽限只支持特定 REPAIR 策略，不能直接授予 M1 新单权限 |

CA 的 10 秒 UNKNOWN 缓存恢复要求写操作之后的新鲜、完整账户证据，且保留原订单风险；它不是 10 秒后自动确认拒单。该模块对未知订单数量及其他订单关闭状态有旧模式假设，M1 并发时需适配，不能直接把 CA 的放行条件接到 M1 上。

当前研究还有一处明确的口径差异：M1 信号层允许 20ms 乱序，模拟成交层只对不超过 10ms 的乱序豁免不确定性，而且不增加排队成交量。实盘需统一说明和记录其处理口径；当前 300 场样本继续保留原版本及变更记录。

## 资金与订单事实

每个机会在任何可能发送订单的异步操作前原子预留目标支出，防止多个新单同时看到足够余额而超额。每份订单风险只计算一次：已成交支出与仍可能成交的剩余金额不能重复计入，也不能漏计 UNKNOWN。

足额或部分成交按实际价格、数量和成本记账；只有明确证明没有提交、拒绝且无矛盾事实，或订单关闭并完成成交核对，才能释放对应未成交占款。迟到成交与终态矛盾须触发重新核对。重启后从持久化日志恢复同一机会和订单，不重新生成买入。

目标 100% 的信号达成率不能越过单场额度、Post-only 或订单身份约束。额度不足、拒单、网络和数据不满足提交条件须记录具体原因，不能以追价、补单或自动转 Taker 来消除未达成记录。

## 信号达成率与收益评价

对每个独立、符合时间、价格和合法报价条件的信号，固定风险目标 `B_i = 1 USDC`，累计已核实买入支出为 `C_i`。失败后的更低价格重试会改变合法目标份数，因此主指标按资金完成度计算：

- 单笔信号达成率：`r_i = C_i / B_i`；成交支出 0.4 美元就是 40%。
- 整体信号达成率：`sum(r_i) / N`，目标 100%。
- 盈利信号达成率：结算方向与拟买方向相同的全部信号的 `r_i` 平均值；包含未提交、未成交但本应盈利的信号。

未提交、最终拒绝、明确未成交按零记录，部分成交按实际支出比例记录。原价、每次重试价、合法数量和签名 ID 均保留；同一信号重试多次仍只算一个分母。资金占用挡住的有效机会仍保留在分母。UNKNOWN 保留分母并标注待核对。另列成交份数／最终合法目标份数；例如 0.19 的合法满单支出 0.9994 美元，资金达成率为 99.94%，份数达成率为 100%，不抹去舍入差额。

检测器必须在活动订单期间继续可靠识别机会，才能建立完整分母；不能只统计成功 POST 的信号。日志缺失、输入断流和无法证明的机会记录为数据不可用，不制造信号数量。订单关闭容差与展示四舍五入不能改变此指标的实际成交分子。

收益展示同时区分信号价全额成交假设、带队列和延迟的模拟、真实成交结算。新增整场挂单规则需要独立回放，不能把旧的严格 RF／EX 到期撤单模型视为等价，也不能据全额成交表假定实盘信号达成率为 100%。

低价区间来自已观察的历史数据，后续固定规则的新样本与选择参数的旧样本分开。每 100 个有效已结算场次比较 PnL、最大回撤、盈利信号达成率和大赢单贡献；无交易的完整场次计零，异常与待结算不计零。300 个已记录场次不等于 300 个有效样本，不足 100 场的最后一组须标明实际数量。历史约 31 美金的回撤不作为实盘损失上限。

## 已确认的运行边界与实现限制

1. **场次收尾和平台结算**：T300 撤单并核对关闭，持久化残仓后交由平台自动结算；关闭未证明时保留风险并阻止切入下一场。M1 不发起新的 Merge；历史已提交且结果不明的事务仍须核对原收据，不清除事实、不重发。
2. **无法成交和异常停机**：确认拒绝可按原价或更低 Best bid 重试，仍须 Post-only Maker；不满足价格或合法报价条件时等待或记录未达成。Ctrl+C／SIGTERM 停止发送，保留已接受／UNKNOWN 挂单及已激活的待重试任务；重启时按持久化 ID 接管挂单，已保存明确失败证明的原任务可在 T240 前继续。没有首次 POST 的过期机会不重放。共享账户锁保留未完成标记，CA 启动阻断。不得改配置或锁目录绕过未决账本。
3. **自有订单**：已按用户确认纳入真实盘口，原先拟议的自有档位屏蔽未采用。一个账号同一时间只运行一个策略，不存在其他策略或人工操作的预期输入。

研究代码未改动；新版使用 `m1_live*` 独立模块和本场 SQLite 账本，沿用原账户锁所在的 journal 目录。参数使用冻结的 cal-16；可选 `config/m1.toml` 只覆盖新版设置，不修改 CA 的 `config.toml`。存在留单时，重启须保留本场原设置。

以下为旧实盘入口的设计记录，当前已被上方公共行情虚拟入口取代。旧入口曾持续运行并支持单场、账户预检、订单接管；其真实账户恢复与网络故障处理尚未满足后台持续运行验收。不能通过修改启动参数直接恢复实盘。

## 首次实盘启动与执行修复

用户随后明确要求清除旧 CA 标记并开始 M1。已核对账户无活动订单、旧场次持仓为零、两笔旧成交均确认且 Merge 收据成功，只清除了账户旧未完成状态，保留旧日志和清理核对记录（`research_outputs/m1_live/recovery/`）。M1 以用户服务 `polymaker-m1.service` 运行，未设置开机自动启用。

启动检查发现，串行重复账户读取会拖过 RF／EX 短授权期。已改为并行读取位置、订单、余额和成交，复用 `_account` 及 `AccountRiskPolicy` 原核对规则；后台刷新不撤销仍在 2 秒有效期内的已核对快照，过期和不一致仍阻断，期间新成交支出继续保守扣留。实测无订单时完整刷新约 220–280ms，修复前单个 CLOB GET 已约 190–200ms，串行读取会积累等待。

发单前对本地已接收待处理帧采用独立的 20ms 排队容差，超过即阻断；这不是放宽源时间乱序、盘口年龄、RF／EX 封口或延长首次授权。持续行情不能要求队列绝对为空。日志新增具体拦截原因和排队年龄，原生 POST 仍即时复核。账户与收尾回归共 399 项通过，随后发单排队边界及原 M1 信号专项 132 项通过（包含 5 个新增用例）。上线调试错过的信号保留为零完成度，未重新授权补发。
