# M1 信号时序排查与观察模式

## 结论与当前运行口径

用户要求先完成信号发生、识别和 POST 标记，不发送真实 POST，并参照 CA 增加实盘容差。
`config-m1` 已设 `observation_only = true`，M1 的默认配置也为观察模式。
在原本可提交的位置记 `sm_m1_would_post` / `WOULD_POST`；不签名、不生成真实订单尝试、
不预留资金、不模拟成交。控制器 guard 和底层 `ExecutionClobClient._post` 均阻止观察模式的真实 POST。
同一 RF 或 EX 最多记一次标记，后续需新的独立 RF 与 AP→EX 过程。资金门槛仍用真实账户信息，
标记不假装消耗 5 美金或释放库存额度。

排查前正在运行的 M1 worker 已收到正常 SIGINT 并退出。开发验证阶段启动了一场新的观察运行，
输出保存在 `research_outputs/m1_audit/observation_20261101_1611.*`。

## 已修正的识别问题

1. **RF 档位变化误清空 AP/EX。** 旧实现删除整个 token 状态，导致跨队列的持续主动卖出也无法累计。
   现在固定 Bid 档位变化只结束对应的回补轮次、RF 和累计成功轮次，保留独立的 AP/EX 成交流窗口。
   RF 仍要求同一档位，不跨档拼凑三次成功。
2. **帧内盘口视图不一致。** 旧实现一边修改临时深度，一边让检测器定时检查尚未提交的旧共享盘口；
   同一条消息替换 Ask、删除再增加档位时，中间状态还可能与消息给出的最终 BBO 不一致。
   现在每条消息先按完整的事前盘口检查，各档数量损失与恢复仍逐条保留；完成整条消息后再对齐和验证 BBO。
   同帧先损失再回补不会被压成净变化零，也不会用最终盘口覆盖事前深度。
3. **减少与 M1 无关的处理。** M1 跳过旧 sigma、OBI 和 REPAIR 价格路径的统计；
   盘口已符合报告 BBO 时复用有序深度，避免重复扫描和复制。没有放宽信号门槛来掩盖处理延迟。

## CA 容差的具体应用

- 源时间倒退不超过 **20ms**：参照当前 `config/config.toml` 的 CA 参数和 `CounterAttack.ordered`，
  记 `EVENT_IGNORED`，不排序、不回填、不更新盘口或覆盖时间，不延长机会寿命，也不清空已存在状态。
- 超过 20ms：仍记 `M1_SOURCE_REGRESSION` 并使对应证据不可用。
- 参照 CA 允许最多 2ms 的源时间轻微超前；更大超前仍拒绝。
- 继续使用 200ms 本地盘口/处理时效、500ms 源证据时效，以及完整窗口闭合后的 50ms 处理预算。
  750ms 窗口、RF 三轮、70% 中位恢复、100ms 保持等业务条件不变。
- AP/EX 依赖成交量完整性，因此不能简单把被丢弃的 SELL 当成零。
  容差内忽略的成交不会贡献 AP 的合格条目、持续性或 RF 冲击；其量保留为不确定上界：
  加入 AP 占比分母、EX 后续卖量及卖压恢复检查。由此避免“忽略卖单反而确认衰竭”。
- 成交价格与事前档位对应仍要求精确匹配，不增加涨跌、价格预测或盈亏触发。

这是用户新授权的实盘输入策略，版本记录为 `orderbook-toolbox-v1-ca-tolerance-v2`，
不能与原研究规格中的零乱序版本混为同一个样本口径。

## 对比重放结果与仍存在的约束

工具读取原始帧，保持记录的接收和开始处理时间、原始顺序及输入水位，使用 25ms 定时器。
帧内处理时间固定，因此它是受控诊断，不能声称精确复刻线程调度，也不能用于推算收益或真实成交。

原有处理延迟也保留在重放中；消费者优化是否改善新的实盘输入，需要单独观察。

对完整观察结束的 SELL AP 候选，三场分别有 45、57、31 个未确认。
其中分别有 45、57、29 个不足最小成交量；42、53、31 个不足三条成交；
45、57、29 个末子窗口没有 SELL。条件可同时失败，以上数字不能相加。
因此 EX 缺少 AP_SELL 前置参照，不是已经完成衰竭观察却漏发确认。

三场各只有一次稳定成功回补，尚未形成同档连续三轮；其后分别被换档、盘口不可用、换档打断。
不合格的回补候选中，成交量不足和未见足够深度损失也占主要部分。
数据工程修复与策略原条件是否适配当前可见成交流，需要分别核验，不凭“每场应该有信号”反向调参。
