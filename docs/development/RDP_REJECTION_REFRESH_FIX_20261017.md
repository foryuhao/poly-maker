# 拒单复核导致快照过期循环的修复（2026-10-17）

## 授权与问题

用户确认先解决 13:00–15:00 批次复盘中的问题 1。
本次仅处理拒单后的账户快照重复全量复核；REBALANCE 存续规则、OBI、数量及最小金额保持现状。

原 `_snapshot()` 在发现 `canceled_submission_proofs` 时调用完整 `_verify_close()`。
这个调用重新查询所有历史 known 订单，每张订单包含多次详情及成交读取。
历史订单累积后，前置复核加账户读取超过原有 10 秒快照时限，产生
`EXECUTION_DATA_STALE → 暂停 → 再次全量读取`，无法抵达后续补仓和常规 Merge 分支。

原始证据见 [24 场复盘](reviews/20261017_1300_1500/README.md) 和
[快照耗时表](reviews/20261017_1300_1500/snapshot_cycles.csv)。
13:10、13:55、14:55 场可还原的单次快照耗时下界分别为 12.076、10.132、10.133 秒。

## 修改后的行为

- 账户快照使用 `_refresh_canceled_submissions()`，仅刷新当前拒单证明。
  所有待复核拒单 ID 共用一次完整开放订单和一次当前市场完整成交集合读取，仍严格读完分页；
  不再额外逐张读取已经完整关闭的历史订单。实际 HTTP 次数随分页数量变化。
- 刷新必须以此前完整关闭证明仍有效为前提，不能用这一局部刷新修复其他失效证明。
- 开始读取前撤回所有待复核拒单证明，恢复 UNKNOWN 和最大资金承诺；
  读取失败、分页不完整时保持阻断，不能沿用原先的 REJECTED 放行。
- 复用原来严格的身份绑定业务回执校验：完整回执形状、精确签名 ID、唯一提交身份、
  无已观察订单/成交/隔离事实。新出现的 REST 订单或成交转回正常关闭核验。
- 只有本次拒单刷新自身推进了证据版本，且 WS 外部版本、分页失败版本未变化、
  已有完整关闭证明集合仍一致时，才能恢复原关闭证明的有效性。
  复核期间其他历史订单出现 WS 事实也会阻止放行。
- 后续账户快照仍检查新的完整成交集合、开放订单与终态矛盾、资金、库存、身份及版本。
  每轮收尾的完整 `_verify_close()` 保持原行为。
- **10 秒上限及计时范围没有放宽或重置**；账户读取本身真正超过时限仍拒绝交易。

没有新增或改动日志事件、字段、措辞；不改历史日志与恢复标记。

## 离线验证

针对性测试使用真实 Gateway、SDK、FillTruth、Tracker 与日志 writer，替换 HTTP/WS/时钟边界，禁止真实网络。

  验证旧全量前置复核本身就超过 10 秒。
- 同一状态下连续两次读取新快照均在原时限内完成，快照阶段没有历史订单详情请求；
  开放订单/成交读取次数不随拒单 ID 数从 1 增加到 3 而增长。
- 真实确认的 YES 5 股库存保持不变，并验证可以继续通过控制器提交 NO 补仓单。
