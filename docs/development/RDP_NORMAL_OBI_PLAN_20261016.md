# RDP NORMAL / REBALANCE 独立流程与 WS 盘口改进方案（决策已确认）

日期：2026-10-16（北京时间）。状态：用户已确认冻结，进入开发；本文作为冻结规范保留。

本版沿用第二版的独立策略过程、WS 替代及在途 POST 关闭设计，并落实最新约束：
状态切换继续依赖确定证据；NORMAL 不要求等量；自身小额挂单影响首版忽略；
普通日志后置且异步写，最小恢复记录在准备阶段完成，避免阻塞信号到操作。
用户已确认 NORMAL 按信号事件+2秒请求关闭，REBALANCE 使用独立3秒租期。
持续同向信号首版只允许入场一次；实盘验证以后再考虑打开重复入场，不能自动启用。
本文件所有新流程仍为开发方案，尚未实现。

审阅分支：`rdp-size-001`。HEAD：`c9136c93cc40d6bc534df6b60610e13df8326c79`。
本方案以当前源码及 `RDP_SM_CURRENT_BASELINE.md` 的后续修订为依据；

## 1. 建议结论

采用独立的 `obi_v1` NORMAL 入场模式：执行进程维护当前市场的官方 WS 盘口，
在既有账户/资金准入完成后，用最新双侧买卖一挂量产生信号；信号侧挂 BestBid，
另一侧挂该 Token 的 BestBid−1 Tick，两腿一个 POST、共享 2 秒成交等待窗口。
网络或数据不合格时暂停新的 NORMAL 入场，继续撤单、确认和风险核对。

需要先接好执行端的实时盘口与最终提交校验，不能只把现有价格加一档、3 改成 2。
NORMAL 与 REBALANCE 各自拥有准入、报价、存续和退出过程；共用行情服务与订单风险底座。
REBALANCE 保留既有修复方向、数量算法及 maker-only 约束，独立管理修复订单。
两阶段都使用 WS 全盘口重建，保留确认、资金预留、Merge 与 Session 隔离。
0.62 美分仍是探索样本的中价预测结果，不能作为每笔挂单的预期净利润。

本轮只更新本方案及派生审阅证据；不修改生产源码、原测试、现有 TOML，不启动交易。

## 2. 已确定约束与本版建议的首版行为

| 项目 | `obi_v1` 建议行为 |
| --- | --- |
| 生效范围 | 仅现有分类器判为 NORMAL，且 T15≤T<T120 的新入场 |
| 输入 | 当前 YES、NO 各自买一/卖一的真实挂量，单位为份；不由 YES 推导 NO |
| 信号 | `I_Y=(B_Y−A_Y)/(B_Y+A_Y)`，`I_N=(B_N−A_N)/(B_N+A_N)`，`I=(I_Y−I_N)/2` |
| 阈值 | `I≥0.30` 指向 YES；`I≤−0.30` 指向 NO；其余为 NONE |
| YES 信号 | YES BUY@YES BestBid；NO BUY@NO BestBid−NO Tick |
| NO 信号 | NO BUY@NO BestBid；YES BUY@YES BestBid−YES Tick |
| 无信号/无效数据 | 不开本轮 NORMAL；不得自动退回旧双边报价 |
| 数量 | 沿用当前 `normal_sizes`、Inventory Skew、Favorite/TargetDelta 及约束调整 |
| 提交 | 同批两腿、BUY-only、GTC、post-only；任一腿事前非法则整轮不发 |
| 成交窗口 | NORMAL 两腿共享信号事件+2秒截止；提交延迟消耗这2秒；REBALANCE 使用独立修复订单租期，初值 3 秒 |
| 到期 | 持续记录关闭意图，撤销未成交订单并完成关闭证明；2 秒不等于已确认或已撤净 |
| 窗内管理 | 首版不追价、不增单、不翻向重挂；断连、盘口失效等硬故障提前关闭 |
| 软信号变化 | 首版记录中性/反向变化，仍按固定 2 秒对照；软失效提前撤单另作对照实验 |
| 持续同向信号 | 同一连续信号区间最多提交一批NORMAL；未成交/拒绝也不在同区间重发；重复入场首版关闭 |

NORMAL 数量不要求等量，配平由既有 REBALANCE 规则负责。现有 NORMAL 并不总是空仓，
`ROUND_HALF_UP(abs(Delta))<5` 仍可能带少量残余，实际边界约为 abs(Delta)<4.5；
TargetDelta、最小量和 Skew 也会使两腿不等量。本方案不强制改为等量。
只有真正配对的等量部分才能计算 `1−pYES−pNO`，残余损益必须单列。

若 NORMAL 带小残余而无信号，本方案暂停新 NORMAL 后仍会保留残余；
不得把它写成“已经修复”，也不擅自改变 NORMAL/REBALANCE 分界来处理它。
这项持仓后果需要在研究统计中显式展示。

按用户判断，当前自身挂单金额很小，首版忽略其对公共盘口信号的影响，
不做自身量扣除、专门去偏或撤单后等待自身量消失的额外门槛。
固定窗口内仍不因瞬时中性/反向自动翻向重挂；软信号提前撤单属于后续独立实验。
确认等待和不等量都是已接受的策略边界，不再作为需要改掉的设计问题。

## 4. 独立策略流程与共享订单底座

```text
Session 内官方 Market WS → RDP 行情适配器 → 不可变双侧盘口快照
                                              ↓
                              Session 协调器（唯一交易写入者）
                              ↙                        ↘
          NORMAL 入场过程                              REBALANCE 修复过程
     等有效信号 → 双腿非对称报价                      查缺口 → 缺口侧 BestBid
     信号+2秒 → 关闭两腿                             独立订单租期 → 撤后重算
                              ↘                        ↙
                       订单生命周期 / 资金预留 / 官方确认
                       未关闭、UNKNOWN、待确认 → 禁止交接

同Session网络监测 → 发布不可变健康快照 → 最终本地Guard
```

“独立过程”指同一 Session 内两个独立策略控制器，不建立两个并发争用账户的交易进程。
Session 协调器串行授予交易权，NORMAL/REBALANCE 不同时拥有活跃提交或修复任务。
两者可共用签名、发送、撤单、核对等低层原语，不能继续共用完整的策略 `execute_window`。

| 项目 | NORMAL 控制器 | REBALANCE 控制器 |
| --- | --- | --- |
| 目标 | 抓信号后配对入场 | 修复已确认的库存缺口 |
| 准入 | T15≤T<T120、NORMAL 库存分类、有效 OBI、网络准入 | T15≤T<T300、REBALANCE 库存分类、可解释缺口与资金 |
| 行情 | WS 双 Token 同代次全盘口 | 同一 WS 权威盘口；不要求出现 OBI 信号 |
| 报价 | 信号侧 Bid，对侧 Bid−各自一 Tick | 缺口侧 BUY@Bid，沿用修复数量及 TargetDelta 算法 |
| 存续 | 信号事件后 2 秒截止，不追价/翻向/补发缺腿 | 独立订单租期初值 3 秒；到期撤净后，按新库存和盘口重算 |
| 提前退出 | 硬数据/网络故障、部分拒绝、市场截止、显式停止 | 修复依据失效、硬数据故障、订单异常、独立租期或市场截止 |
| 完成后 | 关闭证明后重新分类库存 | 关闭证明后判断继续修复、返回 NORMAL 或等待结束 |

REBALANCE 的 3 秒只是迁移时保留的独立参数，不继承 NORMAL 的信号寿命和“无信号不交易”。
首版不做未撤净前的追价替换；若租期内有成交消息，保留 pending 风险，禁止按未确认量补买。
2 秒到期后已 MATCHED/MINED 的部分仍等待官方确认，不能为了快速修复绕开关闭屏障。
小残余仍沿用现有 NORMAL 分类，不因拆流程擅自改变 4.5 附近边界。

### 4.1 执行进程内的只读行情适配器

建议新增 `rdp_sm_marketdata.py`，提取 Shadow 使用的“官方 WS BOOK + DELTA 重建”能力，
复用已有连接、队列与每 Token 的 `OrderBook`，只订阅当前市场 YES/NO；不持有发单能力。
Shadow 仍保持原有独立采集进程，交易不依赖其启动成功、文件写入或采样延迟。
执行与研究共用清晰的数据定义和可测试重建逻辑，不把 Shadow writer/model/JSONL 变成交易依赖。

在新模式下，两阶段报价、Sizing 中的 Favorite、最终 guard 全部读取这一权威 WS 快照。
`discover_current_market` 只做身份/时间/约束发现；M1 改为组合行情 readiness 检查；
M3 不再 `_read_books`；M2 不再以 REST book 冻结或刷新报价。REST book 不进入新模式报价路径，
也不作为 WS 故障时的隐式回退。账户、订单、成交、余额、官方时间与必要市场约束 REST 保留。
legacy 若保留，仅由启动时显式配置选择，运行中不能从新模式自动切回。

不能裸用共享 parser 的宽松行为：现有 parser 会跳过坏 level，通用服务也保留旧缓存。
RDP 适配器必须在应用事件前严格验证当前 condition/token、数值、完整 frame 和侧别；
错误、断线、队列溢出或时钟异常使执行快照失效，等待当前连接代次两侧完整 BOOK 重建。
不得由后续一条 DELTA 把损坏的旧 book 重新标成有效。
若本连接不会主动重发 BOOK，必须重订阅或重连，不能永久等候一条不会到来的全量消息。
Shadow 的坏消息处理部分只清研究模型、未清底层 book，observer 异常也可能被吞；不能原样继承成交易有效性。
共享服务/FL 的原行为保持，避免把本次严格策略扩散到其他入口。

快照至少包含：market/token 身份、connection generation、两侧 snapshot generation、
每侧 bid/ask/对应挂量/tick、源时间、socket接收 wall/monotonic、应用完成时间、
frame/快照序号、有效性和无效原因。单个 frame 的增量完整应用后再发布，
不能把同一批次的半截更新当成最终双侧状态。
本地发布序号不是交易所连续序号，不能据此声称证明了服务端无丢包。
重连/本地丢帧必须失效并重建；若消息提供顶档摘要/hash，按其实际语义做一致性检查，
不得把不明确的 hash 当成已实现的 checksum。跨 Token 时间偏差也须记录并设显式准入预算。

注意 `OrderBook.local_ts` 是处理时调用 `time.time()`，不等于 socket 收到消息的时刻。
应复用队列入口已有的实际接收单调时间；把排队滞后和数据年龄分别计算。
只有 TICK、心跳、TRADE 或重复 frame 到达时，不能把旧盘口刷新成“新盘口”。
不要只因全局事件序号增加就拒绝所有报价：深度不断变化时这会饿死发单。
最终比较同一市场/连接、当前方向、价格/tick约束和时效，允许不改变报价结论的正常深度更新。

### 4.2 纯信号与统一报价决策

建议新增 `rdp_sm_signal.py`，输入不可变快照，输出：
`VALID_YES / VALID_NO / NONE / INVALID`、IY/IN/I、原始四个挂量及 snapshot ID。
用明确数值类型计算，拒绝布尔值、非有限值、零/负有效挂量，阈值包含±0.30边界。
不混入 OFI、动量、概率 Favorite、未来价格或回测最终赢家。

将 NORMAL 和 REBALANCE 的纯报价函数分开，分别由相应控制器及执行前校验调用。
移除执行器从 M3 循环反向导入统一 `make_quotes` 的策略耦合。
传入不可变 `ExecutionIntent`，绑定 phase、snapshot、库存/资金 revision、价格/数量、退出策略及 deadline。
资金/订单/官方 tick 的既有准入全部先完成，再从 WS 冻结最终快照、重算信号和两腿报价。
账户/风险证据与盘口证据独立计时；账户不因盘口替换而降低准入标准。
Tick 初始由官方约束校验，后续 WS tick change 更新且立即使旧决策失效；
缓存的 REST tick 不得覆盖较新的 WS tick，冲突时暂停并重新核对。
不把 Shadow 当前硬编码的 tick 列表当作永久交易所规范；SDK 不支持的 tick 必须明确阻止，不能四舍五入后交易。

没有信号时等待新的有效盘口事件或市场截止，不以固定一秒忙轮询产生重复跳过日志。
价格越界、任一腿不满足 tick/最低份数/1美元金额、资金不足时跳过整个新批次；
不自动夹价、不单发合法的一腿，也不放大订单以规避最低金额。
不把“配对预算”误解为已有利润保证：当前预算是资金占用校验。
首版记录两腿价和及残余风险，不额外引入尚未研究的配对利润硬阈值。

#### 4.2.1 连续信号区间与一次性入场资格

用户明确关闭持续同向重复入场。由 Session 内独立信号跟踪器维护
`episode_id / direction / claimed / consumed`，不能只在 NORMAL 循环内临时保存。
它持续接收有效盘口事件，REBALANCE、关闭核对和确认等待期间也不停止跟踪。

| 事件 | 首版处理 |
| --- | --- |
| 当前YES，后续仍YES；或NO后续仍NO | 同一区间；已经提交则不再开批 |
| 有效NONE后重新出现YES/NO | 新区间，可在全部准入通过后入场 |
| YES直接变NO，或NO直接变YES | 新方向区间；旧批仍按自己的关闭规则处理，新批必须等关闭屏障允许 |
| INVALID、断连、过期、队列丢帧 | 不等于NONE，不重置已消费资格；先失效，重建后同方向仍不得重复 |
| 转入REBALANCE再回NORMAL、Merge或上一批到期 | 不重置区间；不能绕过持续同向只发一次的限制 |
| 两腿都没成交、全部明确拒绝、部分接受或POST后UNKNOWN | 只要POST已经开始，本区间资格已消费；不重发、不补腿 |
| HTTP尚未开始，因门禁/准备未命中而跳过或可靠ABORTED | 未消费，允许在本区间后续新的有效事件上尝试首次提交；不是缓存旧信号重试 |

发送权先原子claim，防止多个WS事件同时排队提交；实际HTTP开始时消费本区间资格。
若已不能证明HTTP未开始，按已消费并保留风险；不能以异常或空响应释放资格。
全局最多一个在途批次，区间已改变则旧claim不得偷偷变成另一区间的订单。

`episode_start`、`signal_event`、`post_started`分别记录：区间起点用于去重；
一次入场的signal_event必须引用真实的新鲜盘口事件，其+2秒deadline建立后不续期。
开始时门禁不满足而未POST，并不消耗未来首次提交机会；之后如入场必须用新的有效事件，
不得把旧快照改时间戳。这样不会把“每区间一次”额外改成“首次穿阈值时未准备好就永远不能买”。
首版不新增中性停留时间或额外阈值：按原±0.30和完整frame发布后的有效标签划分区间，
短暂但真实有效的NONE会结束旧区间；同帧半更新、坏数据不能制造NONE。
这不是“每个市场每方向只买一次”，有效信号区间改变后可再次入场。

启动时第一份完整有效盘口可建立初始区间；WS重连不等于新Session。
异常进程重启不能假定资格从未消费：若无法恢复同市场已消费状态，首版不自动恢复该市场新NORMAL，
先继续未解决订单风险的核对/关闭；不得通过重启清空一次性限制。
当前没有新增必须由用户决定的参数；这些边界按一次性入场语义落实并纳入验收。

### 4.3 两层发单校验与线程边界

准备完成后仍可能发生行情变化、WS断线和网络退化。
保留 Gateway 与 `ExecutionClobClient._post` 两层 guard；在既有资本revision、
官方交易时段、fatal和分页条件上，按 phase 校验各自的信号/行情/网络条件。

guard 在 SDK 线程执行，只能读取带短锁或等价安全发布机制的不可变快照，
不得直接访问可变 OrderBook、SQLite、异步对象或执行 HTTP。
NORMAL 价格必须符合当下该方向的 BestBid/BestBid−Tick 规则；REBALANCE 符合缺口侧 Bid。
两者均小于各自 Ask，不能因 post-only 被拒而自动改为 taker。
改变报价结论时在未 POST 前放弃旧签名批次，安全关闭后重新决策；不在 worker 中改写已签名订单。

网络/信号失效发生在 Intent 之后、HTTP尚未开始时，应产生可解释的 ABORTED 原因，
完成原有关闭核对；不能错误升级成“已发出未知订单”，也不能提前释放真实旧敞口。
POST一旦开始后超时，继续原 UNKNOWN/保留预算/查证路径，不重发同批次。

### 4.4 准备在前，信号到操作不等待日志

当前路径有 `sm_strategy_window`、`sm_quote_refreshed` 及两条 `sm_placement_intent`，
这些 `record` 都会同步序列化并 fsync。不能只减少终端输出或把它们改名成异步任务。

建议拆为以下两段：

```text
准备阶段：账户/资金/官方约束 → 候选价格及数量 → SDK签名/逐腿ID
          → 一条最小 PREPARED 批次记录持久化 → 进入可发送状态

操作阶段：收到当前有效WS事件 → 计算信号/选择候选 → 最终本地校验
          → 原子占用本批发送权 → POST
          （不调用日志writer，不等待flush/fsync，不做额外GET）

事件时间和结果 → 有界内存缓冲 → 独立writer异步序列化/落盘
```

候选准备允许按当前价格分别准备 YES / NO 两个方向的两腿组合；每个候选有独立逐腿ID，
同一准备槽最多选择一个组合、POST一次，未选择的候选永远不能发送。
资本按互斥候选中的最大合法承诺预留，不把4张候选当成已发出的4张订单；
最终仍按实际两腿精确复核25美元上限及官方可用资金。该互斥性必须有故障测试。
REBALANCE 只准备当前缺口侧候选，不需要 OBI 两方向组合。

候选必须绑定市场、连接代次、tick、报价价格、数量/TargetDelta、资金及库存 revision。
纯深度量变化只改变信号时，可选仍匹配的候选；价格/tick/Favorite或风险依据变化则使候选失效。
没有已持久化且匹配的候选就跳过本次信号，后台重建；不能在信号后临时同步补写日志或悄悄重签。
Gateway 需有发送已准备签名订单的受限路径，保留 post-only、原文经济字段校验和两层 guard。
发单前必要的协议正文序列化、HMAC 和发送权校验仍存在，不把必要操作算成可以删除的日志。

最小 PREPARED 记录包含 Session/槽位、全部候选ID及经济字段/风险上界，标识“可能发送”，
不伪造 ACK，也不把可复用的签名或密钥写入普通日志。
准备记录也通过单一writer后台落盘，等待完成才能进入可发送状态；等待期间事件循环继续处理行情和撤单。
崩溃发生在 POST 与事后日志之间时，准备记录使潜在订单仍可追踪：查证所有可能候选，
不能因为没有 POST/ACK 日志就释放风险。发送前后崩溃、重启不得重复使用同一准备槽；
未解决的 Session 不得靠开启新 Session 绕开。现有代码尚无这套恢复接线，需作为开发验收。

这项准备会花时间并可能错过信号，不宣称没有成本：记录首个合格事件到发单的真实耗时、
准备命中率、因未准备跳过的信号和失效次数，不能通过后移信号时间戳把准备延迟隐藏起来。
如果不实现候选预准备，则只能做到普通日志后置、发送前最小WAL仍有延迟，不能声称满足零日志等待目标。

SDK 暖机必须覆盖当前 client 的 tick/version/market约束缓存；WS tick 变化后撤销旧候选，
先校验约束并重建，再恢复。第三版离线探针已确认：传 options.tick_size 但冷缓存时触发1次
stub GET，暖缓存时0次；无真实网络访问。操作段若意外试图读额外HTTP，应在发送前拒绝并回到准备。

### 4.5 Maker 结构的建议与剩余执行问题

在 maker-only、BUY-only、现有配对/修复框架下，首版继续使用已确定的两侧 Maker。
没有当前执行样本证明另一结构更好。以下是机制判断，不是已验证收益排序：

| 结构 | 可能收益 | 代价与建议 |
| --- | --- | --- |
| 信号侧 Bid、对侧 Bid−1 tick | 同时提供入场与配对机会；保持当前修复体系 | 作为首版基线，分别观察哪侧先成交 |
| 只在信号侧 Bid 买入 | 减少对侧先成交的情形，方向暴露更直接 | 上涨时可能排不到，成交后缺少同步配对机会；留作后续对照，不取代首版 |
| 信号侧 Bid+1 tick，仍低于 Ask | 价差允许时可能改善队列位置 | 每份多付一个tick；tick若为1美分，高于0.62美分样本平均中价变化，不能默认划算 |
| 先等信号侧成交确认再挂另一侧 | 配对意图更明确 | 确认等待可能跨过预测期限；不适合当作首版2秒捕捉的主要方法 |

post-only 可以用于不会立即跨价的限价单，最终必须由交易所 post-only 约束保证；
不能把 Bid+tick 自动等同 maker，必须仍低于当时 Ask。
官方约束参考：[Place Orders](https://docs.polymarket.com/trading/place-orders#post-only-orders)。

关键未验证项是成交选择：信号侧涨得越快，Bid 买单越可能不成交；真正成交的子样本
可能与所有信号点的平均走势不同。不能靠准确率或触价重放判定捕捉成功。
至少报告信号侧/对侧分别的提交、接受、成交概率、入队时间、成交后2秒markout及最终修复成本。
公开L2没有逐单队列身份，不承诺精确推算排队成交。

两个过程还应采用不同的行情可用性要求：NORMAL 必须有双Token四个有效L1挂量；
REBALANCE 的必需价格证据是实际修复 Token 的有效 Bid/Ask/tick。
非修复 Token 合法空盘口不等于全局 WS 损坏，不应仅因 OBI 不可计算就拒绝修复。
TargetDelta/Favorite 依赖双Token时，沿用现有无有效Favorite则目标回到0的行为并记录原因，
不得把非法/过期数据伪装成有效Favorite；全局断连、身份冲突、丢帧仍阻止两阶段新增。
repair Token 自身缺少当前报价时不猜价，继续核对/撤单；本版不扩展为无Ask报价规则。
此处是新流程的数据契约拆分，不能让一个全局 `pair_valid` 兼任所有策略的准入。

## 5. 网络与时间预算

前一轮检测使用同安装 SDK 的公共 HTTP/2 暖连接，30次GET全部成功，
RTT中位203.48ms、P95 229.15ms；这是短时读取样本，非发单/撤单或WS端到端保证。
证据：`research_outputs/NETWORK_QUALITY_20261016/probe.json`。

建议新增 `rdp_sm_network.py`，按当前 Session 保存有界样本；复用 SM 实际请求耗时，
必要时后台低频 `/time` GET 暖机。不要修改 SDK 的全局 HTTP 客户端或全局 monkey patch。
在 SM 专用 client/read 组合中观察请求，区分 GET、POST ACK、DELETE ACK，
不能让许多快速缓存GET掩盖最近慢POST/慢撤单。失败与超时单独退化，不能从统计里静默丢掉。

| 参数 | 建议实验初值 | 含义 |
| --- | ---: | --- |
| `normal_entry_mode` | `legacy` / 显式选择 `obi_v1` | 旧入口默认保持旧行为；obi失败不自动降级 |
| `threshold` | 0.30 | 固定联合L1不平衡阈值 |
| `normal_signal_horizon_sec` | 2.0 | NORMAL 从本次因果可见信号事件起的截止预算；替代POST后重开2秒 |
| `rebalance_order_ttl_sec` | 3.0 | 独立修复订单租期，撤净后重算，不是 NORMAL 窗口 |
| `max_book_age_ms` | 100 | NORMAL 两Token；REBALANCE实际修复Token，按socket实际收包时间计算 |
| `max_signal_age_ms` | 100 | 冻结决策至最终POST校验的单调年龄 |
| `max_rtt_p95_ms` | 250 | 近期CLOB请求健康准入参考 |
| `max_signal_plus_rtt_ms` | 500 | 信号年龄+近期RTT预算的保守准入估计 |
| 健康样本规则 | 至少10次；30秒有界窗口；最新样本≤2秒 | 样本不足/过期为UNKNOWN，不能入场 |
| 恢复规则 | 连续3次健康且滚动门槛重新全部满足 | 不因单次快速请求立刻恢复 |

这些是待验证的可配置初值，不是已经证明的盈利最优点。
已有 POST/DELETE 样本退化需影响后续入场；首次尚无写请求样本时，
只允许用公共GET建立初始代理健康证据，明确标记写链路尚未实测，不能为测速发送真实订单。

使用单调时钟计算本地时长；不得把 RTT/2 当作已知单程延迟。
本地盘口新鲜也不能证明交易所源消息没有滞后；源时间差及其时钟不确定性单列。
当前 `/time` 可能整秒，不能拿它硬证实100ms源端延迟或把未来时间误差补成零。
WS接收、队列处理滞后、连接状态和源时间异常都要记录；若严格的源端时延证明不足，
在验收中如实保留，不把本地100ms门槛宣传为已证明端到端100ms。

新 BUY 的健康准入由 NORMAL、REBALANCE 分别执行。撤单、订单查询、确认等风险处理
不受入场开关阻断；连接不良时继续尝试关闭已知订单。
REBALANCE 仍须通过自己的盘口新鲜度、资金与连接检查；不能以“风险修复”为由用旧报价发单。
首版修复也使用 100ms 本地盘口年龄、250ms RTT P95、500ms 决策年龄+RTT预算，
由 REBALANCE 自己的准入策略执行，不继承 OBI 方向条件；以后如需放宽必须单独评估。
网络 RTT 退化时停止两个控制器的新 BUY，优先关闭现存订单，继续查询/确认，不能无限重发。
没有当前健康证据时只核对/撤单并记录未修复风险，不假设网络差时 maker 订单一定能修复。

## 6. POST 未返回时的撤单竞态

### 6.1 当前系统的实际能力

| 情况 | 当前行为 | 结论 |
| --- | --- | --- |
| POST 正常返回 | 注册两腿 ID 后设 timer，按原 deadline 撤单 | 能工作，但 timer 本身不覆盖在途 POST |
| POST 跨过 deadline，随后 ACK | 返回后剩余等待为零，马上撤已知 ID，再核对 | 能关闭，不会从 ACK 重新等完整窗口；实际暴露可能超过窗口 |
| 把 `_cancel_known` 直接前移到 ACK 前 | 当前批 known 为空则直接返回；有旧 ID 时仅撤旧单 | 无法达到新订单到期撤单的目的 |
| 交易所已接单、ACK 丢失 | UNKNOWN、保留承诺资金、阻止继续；open orders 不猜测归属 | 可阻断新增风险，不能自动找回并撤净未知订单 |
| DELETE HTTP 200，逐单 `not_canceled` | Gateway 可能返回 true；官方关闭核对仍会发现 LIVE | 不会据此直接释放资金，但单次任务完成不能代表撤单完成 |
| 取消 POST awaiter | 现有 shield 会继续接管同一次请求，等返回再关闭 | 此能力应保留；取消协程不等于取消交易所订单 |

本轮离线注入复用了原 M1/M2/Gateway/SDK 路径，封禁真实 socket，仅使用 dummy key：
POST 已接单但响应被线程阻塞时，提前调用撤单产生 **0 个 DELETE**；释放晚 ACK 后才撤两腿。
丢 ACK 时模拟交易所仍有两张 LIVE，known 为空、DELETE=0、承诺 **4.85 USDC**、关闭 BLOCKED。
逐单撤单失败时 journal ack=true，关闭仍 BLOCKED；同集合再次调用复用已完成任务，
显式 `verify_close(cancel=True)` 可清缓存后重试。不能把缓存问题说成永远无法重试。

证据：`research_outputs/RDP_NORMAL_REVIEW_V2_20261016/` 的三个 JSON 和 `pytest.txt`。
这些证明当前行为和缺口，不证明下述尚未实现的修复已经有效。

### 6.2 需要实现的订单生命周期

生命周期共享，策略退出原因及计时归各控制器所有。至少区分：

```text
PREPARED → POST_IN_FLIGHT → ACK / REJECTED / UNKNOWN
                   ↓             ↓
             CLOSE_REQUESTED（持续标志，不能被晚 ACK 清掉）
                   ↓
         逐单撤单 + 官方订单/成交核对 → CLOSED / UNRESOLVED
```

`CLOSE_REQUESTED` 是与提交结果并存的状态，不是收到 ACK 前就结束当前批次。

1. 候选准备阶段持久化可能发送的订单身份；信号选择本批时建立生命周期所有者与关闭任务。
   NORMAL `deadline=signal_event_monotonic+2秒`；`signal_event_monotonic` 是产生该次决策的
   实际WS帧本地因果可见时刻，记录socket接收与应用完成时间，并用真实接收年龄执行新鲜度门禁。
   不因重复读取同一缓存或完成准备而产生新信号时间。POST前已拥有deadline；
   worker 在HTTP边界只做内存状态/时间更新并通知计时，不同步写日志，也不等ACK才建立timer。
   例如信号后0.05秒才开始POST，则目标剩余窗口约1.95秒，不是再开2秒；
   本地信号年龄超过100ms时本来就应拒绝发单，不因有剩余窗口而放宽准入。
   同一信号批次不续期，后续正常行情更新也不延长deadline。
   REBALANCE 无2秒预测信号，仍用其独立 `post_started+rebalance_order_ttl`。
2. 到期/硬故障先置持续关闭标志；有可验证的本批 ID 就撤，无 ID 也保留关闭任务，
   不把“没发出 DELETE”当作完成。deadline 不随 ACK、行情更新或信号重算延长。
3. ACK/可信身份晚到时注册订单，并立即检查关闭标志；已到期立即撤，不产生新窗口。
   一腿拒绝就关闭另一腿；UNKNOWN 保留每腿完整风险，不补发或盲重试 POST。
4. 逐单保留 `canceled / not_canceled / transport_unknown`，结合官方订单和成交区分
   已成交、未接受/未可见、仍存活。`not found` 在 POST 仍在途时不能证明以后不会接单。
   对仍可能存活的单持续调度受限重试；每 ID/代次有单一在途撤单，完成后允许必要重试。
5. 即使提前 DELETE 返回成功，也要等原 POST 有明确结果并完成最终核对，
   防止服务端先处理 DELETE、后处理 POST 的竞态。不得假定 DELETE 会为未来接单保留撤单指令。
6. POST 读超时、订单租期、撤单重试、官方确认等待分别管理；不能把 HTTP timeout 简单改成2秒。
   请求线程仍归当前 Session 接管，UNKNOWN 未解决不进入另一策略或新 Session 交易。

**身份恢复是 P0 工程验证项：** 当前 `request_hash=SHA256(batch body)` 不可用作 order ID。
安装 SDK 的 V2 order builder 提供 `build_order_hash(typed_data)`；建议在发送前从
实际签名订单及正确 domain/chain/exchange 计算并持久化每腿预期 ID，身份先登记为
“本 Session 已签名待提交”，与“交易所已接受”分开，不伪造 ACK。
需校验当前支持的签名模式、普通/neg-risk domain、salt 及实际 POST 原文一一对应；
收到 ACK/官方订单必须核对 ID 与全部经济字段。一旦不一致，停止入场并保留风险。
此接线当前没有实现，SDK 有 hash 函数也不等于已证明全链路映射；上线前必须完成可信向量/官方契约验证。
若尚未验证可靠 ID，降级能力只能是“等晚 ACK 并保留 UNKNOWN”，不能宣称已解决丢 ACK 自动撤单。
不以 token/price/size 猜测归属，不扩大为账户 cancel-all，不靠新增 User WS 自动补齐身份。

官方接口明确撤单结果可能部分失败，需检查逐单结果：
[Manage Orders](https://docs.polymarket.com/trading/manage-orders#cancellation-results)。
官方还说明某些 marketable order 有 pending delay 且期间不能取消；maker-only 仍须
强制 post-only，不能把所有慢 ACK 归因于这种 delay，更不能在遇到异常状态时改成 taker：
[Order Lifecycle](https://docs.polymarket.com/concepts/order-lifecycle)。

两秒是本地请求关闭的目标，不能保证交易所订单真实只暴露两秒。
必须报告 deadline→DELETE 发起延迟、POST/ACK、逐单撤单结果、终态与确认时间。
同步 fsync、事件循环阻塞、8线程池拥塞、限速及网络都会延迟关闭；撤单要有保留容量，
至少验证读请求拥塞不饿死撤单。不能通过移除 durable intent 来解决时延。
GTC 没有自动两秒到期；不要未经接口约束验证就把 GTD 当作2秒服务器兜底。

## 8. 日志与评估证据

### 8.1 日志不能阻塞 POST、撤单和 ACK 注册

普通策略/行情/人类显示日志移到实际操作之后，用独立writer批量写；操作线程只保存
必要的固定字段和单调时间到有界内存缓冲，不做日志JSON序列化、终端输出或flush/fsync。
“操作后”指发出POST/DELETE后可由writer处理，不是必须等可能数秒后的ACK才开始记录。
慢POST期间、ACK之后、定时撤单之前，同步日志也不能阻塞事件循环。

ACK 到达后先校验并注册所有可识别ID，再处理已到期/异常侧的立即撤单，最后异步记录；
不得写完第一腿ACK日志再注册第二腿。DELETE 同理，先执行再处理诊断日志。
最小恢复记录按4.4节提前持久化，不以普通日志后置为由丢掉崩溃窗口的订单身份。

writer有单一顺序号，记录事件发生时间和实际写入时间，二者不混用。
队列积压时普通重复诊断可合并/采样并计数，关键订单事实不可静默丢失；
关键缓冲容量在准备阶段预留，容量不足不激活新批次。运行中磁盘失败/关键缓冲不足时，
置内存故障标志、禁止新增并优先关闭现存订单，不通过同步错误日志再阻塞撤单。
关闭后排空关键缓冲并核对写入结果；不能因为“已放队列”就宣称已持久化或允许新交易。
最低恢复能力来自已经持久化的准备记录，事后日志缺失时仍保留不确定风险。

逐tick计算仍只在内存完成，不为每条WS消息同步fsync。Shadow原始采集保持独立，
其文件写入和writer故障不能成为执行WS路径的依赖。

### 8.2 必要评估证据

必要字段：mode、window/session、快照ID/代次、四个L1量、IY/IN/I、方向、
报价offset ticks/实际价格/数量、所用官方tick、各本地年龄、信号冻结时刻、
RTT分类统计/样本数/新鲜度/门禁原因、sign/POST/ACK/deadline/cancel/close时间。
前期proposal与真正提交前final decision分开记录；真正发单引用最终证据。
补充 prepared_slot/candidate、准备命中/失效/未命中跳过、首个合格事件→POST耗时、
writer积压/丢弃合并计数、记录发生/写入时间、deadline前后真实延迟。

盘口证据不能含密钥、认证header或新账户敏感字段。保持现有人类日志脱敏，
JSON与RiskJournal以结构化字段为准，兼容旧日志读取器的缺字段行为。

后续比较当前legacy、同非对称报价3秒、同非对称报价2秒；
价格规则与窗口长度分别对照，保持BaseSize、TargetDelta、资金与时段一致。
报告所有尝试及两腿成交顺序、部分成交、配对率、条件Markout、残余及修复成本、
确认延迟、撤单延迟和最终PnL，不能只统计已配对盈利样本。
当前47场均已被查看，不能重新命名成未见测试；重放不将触价当成精确成交。

另有三项研究与执行口径不能省略：

1. 旧诊断按1Hz取样，实时按事件触发会改变入场样本及权重；必须记录实际触发规则，
   限制每批只能有一个在途提交，同快照不能重复开批，不能直接套用旧0.62美分。
2. 自身小额挂单的公共盘口影响按用户要求首版忽略，不为此新增扣量、冷却或准入门槛。
   重新决策仍需正常的新鲜有效盘口，不重复使用旧快照或旧信号计时。
3. 两腿并非原子接受或原子成交，Bid 对侧减 tick 可能只成交对侧；
   需要分别统计“信号侧先成交”和“对侧先成交”的 markout、确认等待和最终修复成本。
   现有价格规则不保证两腿价和<1，也不保证实际等量；首版记录价和与残余，
   不凭中价 edge 宣称配对必赚，也不未经研究擅自添加新的价和盈利门槛。

| 日志与准备 | 现有同步fsync尚未移出操作段；预准备也可能频繁失效并漏掉信号，需测准备命中/失效、真实信号到POST与撤单滞后；不能只以“零日志调用”证明性能改善 |
| 崩溃与磁盘故障 | 事后记录尚未持久化时，准备订单身份必须仍可追踪；重启不得绕过未解决风险、重复发送准备槽；writer故障不阻塞关闭 |
| 测试基线 | 此前相关全套982通过/3失败，需维护真实schema及历史冻结测试契约，再回归新实现；不由用户选择删除或跳过断言 |

上述是开发任务和新模式上线验收条件，不是必须全部完成才能开始写代码的前置门槛。
签名方式、如何计算ID、writer队列、候选缓存和具体模块拆分不作为用户审批项。
预签名候选准备的复杂度必须由性能收益支撑，先完成小范围验证，避免一开始扩大改造。
盈利性仍是后续执行数据的验证项；现有中价研究不能替代成交条件与修复成本证据。
