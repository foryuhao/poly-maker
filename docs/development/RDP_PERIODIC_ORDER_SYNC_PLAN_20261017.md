# 固定心跳订单同步服务方案（两阶段交付）

初始方案日期：2026-10-17，北京时间；研究基于代码与既有36场日志，研究时未修改交易代码、配置或生产日志，未调用交易API或启动交易进程。后续独立观察实现与验证见 [第一阶段说明](RDP_PERIODIC_ORDER_SYNC_PHASE1.md)，第二阶段实现见 [共享读取与核验接入](RDP_PERIODIC_ORDER_SYNC_EXECUTION.md)。

## 2026-10-17 用户确认的两阶段开发顺序

后续确认：第一阶段旁路由每次`rdp-sm-run`启动、绑定本次主市场并在退出时停止；使用用户外层shell循环12次，不增加内部多市场runner。生命周期绑定不等于第二阶段采用旁路数据。当前使用方式与验证见 [托管说明](RDP_PERIODIC_ORDER_SYNC_ATTACHED.md)。

以下最终架构分两步交付，不能在第一步提前迁移消费者：

1. **独立同步观察。** 独立线程、客户端和连接池，只读同步订单、成交、资金与持仓，输出自己的快照和统计。NORMAL、REBALANCE、FillTruth、资金账本、撤单watcher、网络门控继续使用原路径；新流量不进入生产NetworkHealth，旧`/time`不合并。观察器没有交易授权、订单所有权证明或释放资金的权限。先做离线验证，之后可独立开启一小时观察。
2. **策略接入。** 第一阶段实测可接受以后，才让NORMAL、REBALANCE与关闭/资金核验读取同步服务；此时再移除对应旧查询、整合校时与网络探测、实现写操作版本和终态证明复用。

第一阶段会暂时叠加GET流量，不能宣称已经省资源或提高补仓效率。独立进程运行第一阶段服务线程，可避免共享SDK全局传输、可变游标和生产状态；实际网络带宽/IP限额仍然共享，必须测其对原策略HTTP耗时的影响。一小时测试不是自动启动指令，交付后保留明确采样命令。

“同步市场数据”在本任务中指当前市场订单、成交与账户数据；盘口与OBI仍由原有市场WS负责。下面的消费者接口、操作边界、关闭证明及查询去重描述为第二阶段最终行为。

## 结论与推荐参数

采用一个 Session 内的后台同步服务，统一读取服务器订单和成交，业务模块只读内存或等待新版本。**不提供业务调用的 refresh、force_refresh、读失败后自行查询等入口。** 下单和撤单仍由执行模块发送；本地登记操作不是触发刷新。

- 订单同步目标周期：**1000ms，按两轮开始之间的时间计算**，不是“请求结束后再睡 1000ms”。同一同步流最多一轮在途，慢轮自然延长周期，不补发积压轮次。
- 余额、allowance、Data API 持仓：服务内部另一条 **2000ms** 定时流。订单、资金分开保留完成状态，避免 Data API 慢请求阻塞订单状态发布。只有同时满足条件的组合才能授权交易。
- 500ms 不作为第一版目标。750ms 是后续候选，必须先测完整轮次和请求总量。
- 同步服务是一个逻辑所有者，可用一个 asyncio 服务管理两个定时任务；不要求所有 HTTP 都在同一阻塞线程串行执行。现有同步 SDK 继续通过线程池运行。
- 不同时引入账户 WebSocket、业务触发刷新或新的定价/数量策略。

## 1. 速度评估：一次 HTTP 与一轮核验不同

统计基于既有的 13:00–15:00 共 24 场、15:40–16:40 共 12 场。按每条 `sm_network_request.duration_ms` 计算成功 GET，分位数口径和原始日志哈希见 [分析程序](reviews/20261017_order_sync_design/analyze.py)、[证据](reviews/20261017_order_sync_design/evidence.json)、[完整分组表](reviews/20261017_order_sync_design/latencies.csv)。

|接口|成功请求数|中位数 ms|p95 ms|最大 ms|
|---|---:|---:|---:|---:|
|单个订单详情|9681|219.8|322.0|1903.1|
|未完成订单集合|5548|196.6|338.6|3539.6|
|市场成交集合|6097|198.4|315.2|1872.1|
|余额与 allowance|2750|193.2|358.8|1120.3|

后 12 场单独看，订单详情 p95=323.5ms，未完成订单 p95=332.0ms，成交集合 p95=304.5ms。无需用更早样本掩盖后批延迟。

限制：这些是已有请求的 HTTP 耗时，不含线程池排队、完整分页、整轮校验和发布；`/v2/positions` 没有被这套 HTTP 日志覆盖。没有测出新服务的整轮 p95，也不能据此确定机器和网络的绝对极限。

为保留当前的前后核验，本方案不把所有请求完全并行后直接视为一份原子服务器快照。每个订单轮次有两段：

1. 并行读取完整市场成交、全账户未完成订单，以及同轮 `/time`。
2. 完成第一段后，读取需要核验的订单详情；不同订单有界并行。按固定顺序应用整份成交数据并校验，再发布快照。

上轮末尾的订单详情 → 本轮完整成交集合 → 本轮末尾的订单详情，形成前后观察。新订单第一次取得有效身份后，通常需要下一轮才能形成这个关系。不得把第一次查到的 `404` 当作有效前置身份，也不得因空集合认定订单已取消。

在单页、一个待核验订单、不排队的条件下：

|假设每段网络耗时|两段网络耗时预算|含义|
|---|---:|---|
|300ms|约600ms + 本地开销|500ms 周期已经无法稳定完成|
|400ms|约800ms + 本地开销|1000ms 有一定余量|
|500ms|约1000ms + 本地开销|1000ms 也会轻微超期，需自然延长|

用历史单接口 p95 构造的两段预算约 661ms（338.6+322.0）；**这是预算，不是整轮实测 p95**。由此推荐 1000ms 作为起点。750ms 只适用于实测整轮有余量的环境；若实际 RTT 长期接近 500ms，可固定配置到 1250–1500ms。100–200ms 定时器可以运行，却不能创造同样频率的完整权威快照。

官方当前文档列出的 `/data/orders` 和 `/data/trades` IP 限额分别为 500 次/10s，余额接口为 200 次/10s；本方案常规请求量远低于这些单接口数值。但同 IP 其他进程、分页和服务端节流仍需计入；**限额不是速度保证**。来源：[Polymarket Rate Limits](https://docs.polymarket.com/api-reference/rate-limits)，2026-10-17 核查。

## 2. 每轮查询什么，怎样避免越跑越多

|数据|调度|读取与保留方式|
|---|---|---|
|本市场完整成交集合|每个订单轮次|完整翻页一次，解析后更新所有本 Session 自有订单，不按订单重复获取|
|全账户未完成订单|每个订单轮次|完整翻页一次，保留外部订单检查、资金占用和终态矛盾检查|
|订单详情|每个订单轮次的第二段|活动、UNKNOWN、待确认、证明失效或严格拒单证明待复核的 ID；同一 ID 每轮最多读取一次|
|已完成订单证明|本 Session 内复用|保持原始签名身份、成交集合、累计量、终态与版本；每轮全量集合核对，发现新事实即失效|
|余额、allowance、持仓|独立固定2000ms|完整结果才形成资金版本；沿用当前资金与持仓一致性规则|
|市场身份、交易合约元数据|初始化和现有失效规则|不为每次业务读取重复查询 Gamma 或合约静态配置|
|盘口与 OBI|现有市场 WS|独立于订单同步，保持现有新鲜度与信号规则|

不是永久忽略旧订单。以下情况均重新进入待核验集合，并立即撤销相关交易授权：出现新成交或状态变更、分页中的已观察成交尚未对上、终态订单重新出现在 open orders、UNKNOWN 回执、严格拒单证明异常、merge 或其他账户事实变化。

Session 结束的完整复核由服务依据市场截止时间和本地执行状态自行安排，完整覆盖本 Session 已知 ID。分批并发读取，未完成不宣布关闭成功；也不让业务模块自行绕过服务查服务器。下一个 Session 新建服务和版本空间，不读取上一个 Session 的日志作为启动锁；真实账户风险检查仍沿用现有规则。

并发建议：订单流第一段最多3个独立读取，第二段订单详情最多4个，资金流最多2个，总 GET 并发上限6；现有 SDK 8线程池留出至少2个位置给其他操作，DELETE继续使用独立撤单线程池。具体传输池必须验证隔离，不能只是增加 `gather()`。

## 3. “只读内存”如何保证不会使用旧状态重复下单

服务唯一发布不可变版本，至少包含：Session/market 身份、快照版本、轮次起止时间、各来源实际请求起止时间、分页完成状态、订单与成交、终态证明、资金版本及其时间、当前阻塞原因。发布时整体替换引用，读者不持锁等待网络。

执行模块仍必须同步完成本地操作登记：

- POST 前登记精确签名 ID、数量与价格，预留资金，增加操作版本。
- POST、DELETE、merge 的开始、返回或不确定结果都更新本地事实；在途操作不能被服务器空列表覆盖。
- 取快照准备下单时，原子检查版本并预留本次额度；不能先读出余额，再跨过一个异步等待重复花费。

这些登记用于防重复提交、保留 UNKNOWN 风险，并不改变下一次定时查询的时间。服务在下一拍自行读这些事实。

授权规则：

1. 版本号增大不等于数据覆盖了刚才的操作。相关证据请求必须在需要覆盖的 POST/DELETE/merge **结束之后开始**；操作仍在途则继续等待。
2. 新订单只有完成有效的前后身份/数量检查，且末次订单已终态、完整成交集合与累计成交量/关联 trade 对齐，才可释放未成交预留。
3. MATCHED/MINED 不冒充 CONFIRMED；已有已观察成交、部分分页和 late fill 风险不能因新一轮“未查到”而被抹掉。
4. 资金和持仓使用自身采集时间及操作版本检查，不因订单流刚发布而变新；新成交/merge 后须等待覆盖该变化且账实一致的资金版本。沿用现有10秒数据上限，它只是上限，不是允许无视新操作使用旧资金。
5. 已验证的严格 `Already canceled` 证明保留其现有条件、唯一精确 ID 和后续新事实失效规则；普通404、超时和列表缺席都不是拒单证明。
6. 当前 NORMAL/REBALANCE 交易准入、外部目标订单检查、资本上限和持仓容差全部保留。

需要一并解决撤单重试与证据边界的配合：当前 watcher 在完整关闭核验结束前可能持续 DELETE；如果每次 DELETE 返回都推进边界，而 watcher 又等最终证明才停止，就可能永远追不上。改为 POST 已排空、且快照已观察到当前订单的可信终态后，watcher停止新增重复DELETE，排空已经在途的DELETE；服务再取得覆盖最后操作的完整证明。这个“停止重复发请求”条件不释放资金，也不授权下一单；出现新LIVE/未知提交/矛盾则重新启用必要撤单。已有终态观察还必须通过身份检查，不能用open orders缺席代替。

消费者接口只需要 `latest()` 和 `wait_after(version, predicate, deadline)`。后者等待服务发布的通知，在内存中检查条件；不发网络请求，不按毫秒忙轮询，不使用固定 `sleep(2 * heartbeat)` 代替核验。

## 4. 一两拍能解决什么

例：目标 H=1000ms，当前订单轮次的两段网络耗时合计 R=800ms。POST 在某轮开始后才结束，该轮不能作为覆盖 POST 的新证据：

```text
t=0.0   第1轮开始
t=0.1   POST 返回；第1轮开始早于它，不用于证明该操作后的状态
t=0.8   第1轮结束
t=1.0   第2轮开始
t=1.8   第2轮结束，首次取得操作之后的有效订单观察
t=2.0   第3轮开始
t=2.8   第3轮结束，可形成前后检查；若终态与成交确认均满足则继续
```

这是调度示意，不是实测。正常无超期时，首次操作后完整观察最多约 H+R；若需要两次新观察，最多约2H+R。资金流可能需要等待其下个2000ms周期；服务器副本尚未更新或 CONFIRMED 未出现时还要继续等。

因此可以取消“业务主动催刷新”，但不能承诺“固定等两拍就无条件继续”。若 DELETE 此后才返回，或出现新的写操作/新成交，相关证据边界也随之更新。健康未成交收尾可把2–4秒作为首轮验证目标；不能承诺已成交订单也在这个时间内完成平台确认。

下单、有效反转撤单、NORMAL原定2秒期限、REBALANCE3秒期限和市场截止仍走现有独立执行/撤单路径，不等待下一拍。后台同步只负责收集和核验证据。

## 5. 资源预算与网络异常

“消费者多读几次内存不增加 HTTP”可以保证；“固定高频轮询必然比旧程序总请求少”不能直接保证。36场日志记录了42480次GET，按36×300秒名义市场时间约3.93次/秒，且不包含Data API持仓请求，也不是峰值速率。

按单页、没有失败重试估算：

- 订单流每轮为2个集合GET + K个待核验详情GET；K是需要核验的订单数，不是历史总订单数。
- 1000ms订单周期、2000ms资金周期：业务读取约 `3 + K` 次GET/秒（2个集合、K个详情、平均1个资金/持仓请求）。
- 正常状态把当前重复的快照校时与独立 `/time` 保温合并为同一份1000ms采样，约再加1次/秒；**不让每个消费者额外校时**。
- 网络暂停/恢复期间保留现有0.5秒恢复探测节奏、3个有效快速样本及2/4/8秒冷却规则，由服务内部定时安排；不把旧的正常样本当恢复证明。此时不能承诺总请求一直等于常态预算。
- K=1时常态预算约5次GET/秒；K=0时约4次/秒。周期都减半会明显增加请求。分页、最终全量核验和异常均须单独计数；不能把这个预算说成实测总量下降。

主要收益是：消费者数量不影响查询次数、当前关闭中的约4N串行查询变为共享集合和少量待核验详情、整份CONFIRMED在读取后一次应用到所有自有订单。旧订单完整证明复用必须通过失效规则验证后启用，否则先保留完整核验，不能冒称复杂度已经与历史订单数无关。

异常处理：同一流不重叠，不积压周期，不在失败后立刻递归补查询；失败和不完整分页不更新成功采集时间。部分页新观察到的风险仍被保留，并令授权失效。超时后需要持有并排空真实SDK线程，不能取消await后马上启动另一轮造成隐藏重叠。复用连接池，特别是当前每次持仓查询新建的HTTP客户端。撤单与市场WS继续独立工作。

## 6. 实施顺序与验收

1. 建立纯读取收集器与快照发布器，拆开SDK全局`last_trades`、分页cursor、账户policy和processor的隐式共享修改。收集器每个请求/轮次独占分页状态；已观察事实由服务串行接入，不能在失败时丢失。
2. 使用上述两段读取和跨轮前后观察，把整份成交统一应用到所有自有订单，保留严格验证器。独立时钟/健康探测改由服务统一拥有。
3. 迁移`_snapshot()`、`_account()`、`_verify_close()`、FillTruth、拒单证明复核和确认等待的服务器读取，全部改为消费服务证据。保留写操作、独立撤单与期限，处理上述重复DELETE与证据边界相互等待的问题。
4. 经失效场景验证后复用已完成证明；最终完整核验也通过服务的内部状态调度完成。Session结束排空任务后销毁服务。

针对性验证：POST返回前后交错、撤单先于POST回执、在途请求跨过操作边界、late fill、旧终态矛盾、MATCHED→CONFIRMED、partial pagination→失败→重试、余额/持仓滞后、merge、未知提交/严格拒单、消费者取消等待、跨Session隔离、同轮并发读的状态隔离。已有相关测试必须继续通过。

性能验收要同时记录：整轮开始间隔与完成耗时p50/p95/p99、最旧来源年龄、超期/失败率、线程池排队、HTTP与分页数、每市场GET/DELETE总量、关闭耗时、官方CONFIRMED首次被本机读到至本地应用的延迟。增加多个消费者不能增加服务器请求数；同一ID不得一轮重复读详情；市场成交集合不能按订单重复获取。

先以1000ms做受控验证；只有实际订单轮次p95低于约600ms且资源预算有余量，才考虑750ms。500ms候选需要更短的实测整轮时间和足够余量；在用户设定的300–500ms RTT、两段串行核验下不应承诺达到。若1000ms经常超期，则固定调到1250–1500ms，避免为追求账面心跳制造并发积压。

本方案不改变OBI阈值、NORMAL信号侧、报价、最小下单金额/数量、补仓数量、挂单期限、盘口规则及生产日志措辞。收益来自状态共享、去重与并发读取，最终成交与盈亏仍需后续市场样本验证。
