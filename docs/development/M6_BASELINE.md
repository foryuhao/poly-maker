# M6 独立基线

2026-11-13 用户授权开发，未授权本轮启动。M4 基线历史任务已结束；M4 实盘不属于本次变更范围。

## 已确认合同

- 仅 M6「撤供留托」：当前有效 RF_BID 与 LW_ASK 重叠；使用此前 24 小时 v7 测试的冻结信号实现，不调阈值。
- 原信号锚定价 `0.02 <= p < 0.20`，配置为 `config/m6.toml`。该配置与 M4 的配置无继承、覆盖关系。
- 挂价沿用 M4 基线的原锚定价，不使用原研究执行器的 `min(anchor, best_bid)` 改价。
- 每笔模拟风险 5 USDC，每场总占款 10 USDC；每方向一个已 POST 独立机会；数量向下取 0.1 shares，满足平台 Maker 最小量。
- 新单窗口为 `[T15,T240)`；保留现有首次 POST 至少 400ms 的剩余信号预算。信号过期、行情质量、名额、预算等跳过原因必须记录。
- 新口径：POST 后至本场 T240（含），同 token 有效 Best ask 不高于原锚定价减 POST 时 1 tick，才按原 POST 价格和数量全量模拟成交。ACK 只是提交应答。触价盘口数量不限制本约定模型的模拟成交数量。
- 无有效触价证据时记录未成交、模拟撤单及诊断，完整且官方已结算场次收益为 0。行情缺口本身不排除完整已结算场次。
- 旧口径：同一批 POST 立即按原价原量全量模拟成交。仅正式结果确认后记入收益；不完整、缺失、未结算、待观察窗口单列。
- 收益从新基线首场的初始 0 独立累计，不拼接 M4 或旧 M6 研究收益；手续费、返佣均不计入此 Maker 基线模型。

此模型与旧 M6 研究的「直接 SELL 穿价、数量封顶、部分成交」不同，不能把曲线差异直接归因为信号变化。

## 隔离边界

入口为 `python -m polymaker.m6_baseline.run`，只有基线模式，无 `--live`。不加载真实钱包配置，不提供真实下单、账户成交或仓位查询。订单签名使用一次性虚拟密钥；最终 POST 为本地模拟应答。公共行情和官方结果只经公共 GET/公共 WS 读取。

所有新运行数据位于 `research_outputs/m6_virtual/`；锁、会话、账本、结算、统计起点都独立。停止标记仅为 `runtime/trading-control/m6-baseline-stop.json`，不修改或删除任何 M4、人工或余额保护标记。

为避免修改 M4 实盘正在依赖的模块，M6 在独立包内保留基线执行、记账、观察、结算的隔离副本；不改 M4 源文件，不做运行时 monkeypatch。中性行情传输和 SDK 检查组件以只读导入复用。虚拟 SDK 的 `m4_v2` 字符串是既有执行接口枚举，不能据此认定加载了 M4 信号。

`_signal_v7/` 为冻结信号资产，原文件逐字节保留，不格式化或修改。原 v7 无按策略选择接口，适配层只允许创建 M6 campaign；原始完整检测器与适配器的候选以 token、锚定价、确认/失效时刻、RF/LW 证据时间核对，排除进程本地事实 ID 差异。源路径与 SHA256 见 `research_outputs/analysis/m6_baseline_development/provenance.json`。后续更新冻结资产必须重新核对语义，不能静默跟随 research 目录变化。

## 2026-11-14 队列误判与执行调度修复

本次只修改 M6 独立包。冻结信号、共享行情/SDK/日志模块和 M4 配置不改，
不启动或重启基线及实盘。完整链路验收后的 M6 停止状态保持。

- `capture.py` 由 M6 自己管理有界收包队列。应用行情与移除对应收包记录持有同一把锁，
  避免 SDK 线程在两步之间把已处理消息误认成积压。相同时间戳的多条消息仍逐条计数；
  真正未处理的消息仍执行 20ms 保护。读包与消费公平调度，不丢帧、不合并帧。
- 提交前的机会落账、预算预留、签名身份和结果落账在工作线程中完成，等待 FULL 持久化成功，
  不持有行情锁。落账后重新检查当前信号、停止状态和准入窗口，失效机会保留明确跳过记录。
  POST 起点与触价事实的原子持久化仍保留；不以牺牲证据或重启安全换延迟。
- 真实 SDK 签名使用独立的 spawn 进程，避免纯 Python ECC 与行情抢同一 GIL。
  每次运行只预热一次，跨市场复用进程；仅传一次性虚拟密钥，禁止网络连接及 HTTP 路由，
  不继承真实钱包或客户端对象。返回原 SDK 签名对象，父进程仍检查签名请求体与最终准入。
- 积压导致的未发送订单按消费进度唤醒，替代固定 100ms 等待；积压未推进时不反复准备订单。
  每次重试仍全量检查当前信号、行情、预算、名额、首次至少 400ms 剩余预算及 T240。
  已开始 POST 的异常仍保留原有退避及风险记录，不能当作未发送直接重试。
- 新增提交检查时的队首、处理中消息、待处理条数和输入版本，以及实际落账等待耗时，
  便于下一次运行区分真正积压、队列竞态、签名耗时和磁盘延迟。

离线回归包含队列/SDK 确定性交错、同时间戳多消息、消费失败、订阅失败/断线清理、
预提交与最终检查阶段的积压重试、落账期间信号失效、延迟签名跨越剩余预算/T240、
签名身份恢复验证、ACK 后诊断失败不降级成交应答，以及原有预算、触价和恢复测试。

前后各 30 组有 fsync 的合成对照：每组最大事件循环延迟的中位数为 6.86ms → 1.23ms，
信号至模拟 ACK 总耗时中位数为 27.70ms → 31.99ms。合成输入处理更及时，但总耗时未改善；
测试使用共享主机，不能推断真实信号覆盖率或历史三笔一定能成交。当前没有新增生产运行验证。
证据与详细限制见 `research_outputs/analysis/m6_execution_fix_20261114/`。

本轮 M6 独立修复保持冻结信号、价格范围、400ms、预算、方向名额与 T240 不变：

- 所有正常准入都等待行情或任务完成事件，替代固定 10ms 轮询；10ms 仅保留为计时器兜底。
  等待使用 advance 之前的输入序号，防止落账期间收到的消息被清除通知；不取消 SDK/提交任务。

- 预留后、签名后、日志屏障前及时复核，已结束或余量不足的机会不再继续无用准备。
  提交前仍等待 FULL 持久化及日志屏障，真实 SDK 最终检查保留。
- 不再把所有最终检查失败统一落成 `M6_FINAL_GUARD_ENDED`；保留实际原因及检查阶段。
  新增每机会落账排队/执行/回传、签名工作进程 CPU/排队/回传、日志屏障计时。
- 每次启动固定代码指纹，避免修改磁盘文件后把旧进程错误标成加载了新代码。

这些是尚未加载的离线修改，不自动重启 M6，也不改变原始事实或历史 PnL。
减少等待不证明历史机会必能下单或成交；行情质量保护不会因覆盖率而绕过。
