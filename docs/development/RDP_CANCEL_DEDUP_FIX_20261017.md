# 重叠撤单去重与合并收益报表修复（2026-10-17）

## 问题与修改

11:15 场（Session `505876544e8a47419e6337ef4b154adc`）的 w2 同时撤当前订单 `{B}` 和全部已知订单 `{A,B}`；
w3 同时撤 `{C}` 和 `{A,B,C}`。旧实现按完整订单集合生成 operation_id，同一次关闭被统计为两个独立慢操作，
导致 2 秒和 4 秒的重复慢请求暂停。

DELETE 在有批次归属时，统一使用 `cancel-batch:<window_id>` 作为逻辑操作 ID。
定时撤单、全量关闭、该批次的重复撤单以及未解决批次的后续显式清理共享这个身份。
归属在 HTTP 调用开始前捕获，避免线程等待期间客户端上下文变化导致响应被归到下一批。
没有批次归属时沿用订单集合的范围 ID，不把所有未知清理合并为一个操作。

每次实际 HTTP 请求仍有独立 request_id、原始 `request_scope_id`、耗时与结果；
30 秒原始 p95 和批内慢写标记仍保留。不同批次独立计数，即便它们请求的完整订单列表相同。
超时、连接错误、5xx、429 仍按原规则立即暂停，不受慢请求去重影响。
本修复不减少实际撤单、不改变关闭证明、单侧 NORMAL、REBALANCE、网络阈值或订单期限。

合并收益报表此前只根据剩余库存估算配对收益，完全合并后返回 0，丢失已验证的收益或亏损。
现改为：

- `realized_merge_pnl`：已验证回收抵押品减去这些合并所释放的确认成交成本，属于合并毛收益。
- `unmerged_pair_pnl_estimate`：剩余未合并配对库存的估计收益。
- `theoretical_pair_pnl`：以上两项之和；任一未合并估计不可验证时继续标记不可验证。
- 当所有配对库存已合并且官方关闭证明通过时，`sizing_report.pair_pnl` 填入已验证的合并毛收益。
- 未配平残仓的损益、交易净收益、返佣和最终胜负没有权威证据时继续 UNKNOWN。

终端增加明确的已验证合并毛收益、未合并配对估计两项。未知或失败的合并不会生成已实现收益。
重复构建报表从已有确认账本计算，不重复累计收益。旧 JSONL 保持原样。
