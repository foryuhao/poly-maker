# 第一阶段：独立只读同步与一小时观察

最新使用方式：按用户确认改为由原`rdp-sm-run`托管本次Session旁路，外层shell循环12次。见 [主进程托管说明](RDP_PERIODIC_ORDER_SYNC_ATTACHED.md)。本文保留独立观察命令作为可选诊断入口，不必与托管模式同时启动。

日期：2026-10-17。开发基线 `Pilot-x12`；实现位于 `feature/periodic-order-sync` 独立工作目录。本阶段不接入NORMAL、REBALANCE或执行器，也不启动、停止、重启它们。

## 两阶段边界

1. **当前阶段：先测同步服务。** 独立进程内一个后台调度线程，最多六个独立HTTP读取工作线程。自己的SDK认证客户端、HTTP连接池、分页状态、快照与统计文件。只GET，使用已有API key的GET派生，不创建新key，禁止POST/DELETE和余额更新GET。
2. **后续阶段：再接入策略。** 一小时实测后再决定接入。届时才迁移NORMAL、REBALANCE、FillTruth、关闭核验与资金读取，才去掉旧查询、整合`/time`和生产NetworkHealth。

第一阶段的“市场数据”为当前BTC五分钟市场的订单、成交，以及账户余额/allowance/持仓。盘口与OBI仍用原有市场WS，本模块不另做一套盘口刷新。

## 已实现

- 订单目标1000ms、资金目标2000ms，开始到开始计时；独立定时流，同流不重叠，慢轮自然延长而不追赶积压。资金慢读取不阻塞订单快照发布。
- 订单轮先并行取`/time`、完整账户open orders、完整本市场trades，再查询最多四个待观察订单详情；更多ID公平轮转，单独报告未覆盖数量，不把未覆盖轮次标为完整。
- 账户轮取余额/allowance与完整Data API持仓，复用私有连接，不为每轮新建客户端。
- 以官方时间锚点跟随BTC5m市场，换市场重新取得元数据、清理市场内观察；账户来源保留自身时间和作用域。切换前后的旧快照不会被重新贴成新市场数据。
- 每个读取/分页有独立作用域、请求ID、起止时间与完成状态。分页循环、缺游标、格式或身份异常不是成功空列表；部分已验证观察保留为partial。
- 不可变快照。失败保留last-good原时间，发布新版本不把旧数据变新；业务读取内存不发HTTP。
- 完整成交一次处理所有观察到的账户相关maker legs。已观察终态后出现新成交/状态变化会重新查相关详情，不能永久缓存。记录订单累计量与完整成交集合的观察差异。
- HTTP失败在观察器内部退避2/4/8秒，并支持数值Retry-After（上限60秒），不修改生产网络门控。观测数据不能充当生产恢复探测样本。
- Ctrl+C/SIGTERM与到期停止会唤醒定时等待、排空真正的在途读取，然后关闭连接。无法在等待期限内排空会明确报告失败，不把取消await当作I/O已经结束。
- 输出独立采样文件，记录observer源码SHA256、完整请求/轮次证据、失败、数据年龄、观察差异与进程资源。事件队列有界，丢事件计数非零时测量报告FAILED，不能静默宣称统计完整。

这是观察器，不是账户真值或关闭证明：未看到服务器尚未接收的本地签名ID；不登记交易所有权、不更新生产账本、不释放资金、不生成交易许可。所有快照明确`trading_authorized=false`。本地写入版本及严格关闭授权属于第二阶段。

## 一小时运行命令

以下是待执行命令，开发验证期间没有启动真实服务器采样。使用原运行配置与同一个env文件，让观察器沿用相同代理环境；凭证不复制进开发目录或输出文件。

```bash
cd /home/ubuntu/poly-maker-order-sync
PYTHONPATH=src:tests /home/ubuntu/poly-maker/.venv/bin/python \
  -m polymaker.rdp_sm_sync_observe \
  --config-dir /home/ubuntu/poly-maker/livecfg \
  --env-file /home/ubuntu/poly-maker/.env \
  --duration-seconds 3600 \
  --order-ms 1000 \
  --account-ms 2000 \
  --output-dir /home/ubuntu/poly-maker/research_outputs/periodic_sync
```

命令本身不启动交易。若原策略正在运行，二者并行观察；若原策略没有交易，同步服务仍可测网络与刷新，但不能据此判断成交状态传播或补仓效率。测试过程中需要结束观察器可直接Ctrl+C，原策略使用原进程和原路径。

每次运行产生独立UTC时间+随机ID目录：

- `manifest.json`：目标周期、时长、源码哈希及观察模式。
- `events.jsonl`：独立HTTP、读取证据增量、市场切换、轮次、成交状态观察、数量/关联ID对比。
- `summary.json`：正常到期/中断/失败、实际时长、是否排空、丢事件、延迟分布、失败与覆盖数、CPU及进程峰值RSS。

一小时会跨约十二个五分钟周期；若未对齐市场开始，首尾市场可能不完整，不能直接称为十二个完整市场。退出排空时间可能使总时长略超过3600秒。中断或启动失败不冒充一小时测试完成。

## 怎么判断效果与是否恶化

先看**服务本身**：

|项目|检查内容|
|---|---|
|整轮与HTTP耗时|分别看p50/p95/p99/最大值；周期1000ms不等于每个快照都在1000ms内完成|
|实际刷新|开始间隔、发布来源年龄、超期次数；失败时数据年龄应如实增长|
|完整性|分页失败、读取失败、未覆盖ID、部分观察、丢事件及市场切换边界|
|状态传播|CONFIRMED被读取到观察器应用的延迟；这不是交易所真实首次确认时间，也不是原策略的应用延迟|
|观察一致性|订单累计量、trade集合和关联ID是否对齐；两次读取之间可能成交，瞬时差异须结合时间和后续轮次判断|
|资源|额外HTTP、CPU占单核比例、观察器进程峰值RSS；不能当成原策略进程的资源变化|

再看**原策略是否被拖慢**：对照观察开启前最近完整市场与开启期间完整市场的POST/DELETE RTT、网络暂停、收尾耗时、错误/拒单及残仓。两边的市场信号、成交频率和订单数不同，不能只比较最终盈亏或把所有变化归因于观察器。此前36场提供历史参考，不能替代同时间附近的对照。

第一阶段保留旧查询，会增加流量：单页、K=0–1个待观察订单时，常规约增加4–5个GET/秒，约14400–18000个GET/小时；实际受分页、退避、元数据与待观察ID数影响。独立客户端不能隔离共享网络、代理和IP限额。若原策略延迟/暂停明显增加，先停止观察器，检查并发与周期；不为测试修改原策略保护。

这轮能回答“同步是否够快、够完整、是否拖累旧程序”，不能证明“补仓已经加速或总GET已经下降”。后两项要在第二阶段去掉旧查询并接入后验证。一小时结果不足时保留第一阶段继续采样，不自动进入第二阶段。
