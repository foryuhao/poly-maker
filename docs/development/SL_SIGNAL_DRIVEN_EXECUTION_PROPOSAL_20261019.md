# SL信号直接驱动执行：改进方案

本版已由 [V2：新单先发、并行撤单与反向修复](SL_SIGNAL_DRIVEN_EXECUTION_PROPOSAL_V2_20261019.md) 更新。下文保留为上一版设计记录；其中“双成交尚待接受”“反向尾仓不继续修复”和撤单优先的建议已被最新需求替代。

日期：2026-10-19。状态：方案草案，未开发、未上线。

目标：SL一旦由实际运行的策略识别，立即发出订单操作；不把整账户REST刷新或全session关闭核对放在每次撤挂之前。异常、回执与成交事件到达后，再推进执行。

依据：[固定24场执行研究](reviews/20261019_repair_sl_execution_24/README.md)。其中22轮SL、47次POST：识别SL至首次本地观察MATCHED平均8.071秒；7轮需撤TP时识别至首个SL POST平均2.974秒，其余15轮约31ms；25次撤换平均2.679秒。以上是旧流程实测，不是本方案的收益预测。

## 1. 范围与不变条件

- HD/TP/SL策略、阈值、SL不可回退、TP定价保持现状；本方案不修改NORMAL信号或开仓策略。
- 仍为Buy Only、Maker Only、零费用假设。SL报价仍为最新本地对侧ask减一tick，保持原有价格追价条件。
- NORMAL在T120停止开新仓，T180强制SL，T240禁止新REPAIR POST并撤余单，进入Merge阶段。
- session资金上限15 USDC，实际Delta上限5 share；已有实际超限时沿用必要修复优先的恢复规则。
- 实际净敞口绝对值≤2.5时不发新修复单，立即请求撤销已不需要的修复余单；不清零库存和成本。
- 实际净敞口严格小于0.1才满足原有配平口径；未决订单仍可能成交时，不能结束episode或重启NORMAL。
- Data API的0.01核对容差、已知尘量省略规则保持；MATCHED不因等待而自动升为CONFIRMED。
- 无法证明原始经济仓位时不捏造SL输入。可以持续跟踪价格并准备意图，实际SL信号仍使用已确认的策略输入规则。

## 2. 总体执行流程

```text
策略识别SL / T180强制SL
    ↓
发布带episode与版本的SL执行意图
    ↓
本地原子登记资金、Delta和订单在途预占
    ↓
立即请求撤销旧单；本地额度允许时同时POST新SL单
    ↓
接收订单回执、盘口、成交、超时等事件
    ↓
立即调整执行目标、报价及余单；必要的查询在后台进行
```

这里的本地预占只是进程内的原子记账，不发起REST请求，也不等待外部确认。

在外部写入前保留必要的、能按签名ID恢复的提交意图。复用已持久化候选或最小提交日志，不等待整批诊断日志flush；不通过丢弃订单可恢复身份来换速度。

背景账户/交易同步一直运行，结果通过事件更新本地状态。后台发现真实冲突时立即撤风险订单并暂停受影响的新BUY，而不是把所有正常SL操作都串行排在一次全量同步之后。

## 3. 直接进入SL

当HD→SL时：

1. 立即按已知实际缺口和当前本地盘口生成对侧买单。
2. 同一轮本地事件处理内完成预占并发出POST。
3. 若原始NORMAL订单仍可能继续成交，同时发出撤单；其余量仍计入风险区间。
4. 不等待周期性positions/capital刷新，不等待固定2秒复核定时器。
5. 本地盘口缺失、连接已知失效或数量不可用时，能立即发出的撤单仍立即发出；BUY按相应事件恢复，不用旧价盲发。

历史路径T64首次满足SL、系统T72才处理到，与系统T72发出信号后执行慢是两种延迟。本方案首先消除信号之后的串行等待；不会声称未经证明的历史仓位在T64就已经具备合法下单条件。

## 4. TP→SL切换

SL意图生效时，立即：

- 递增SL执行意图版本，使全部尚未真正POST的旧TP候选失效；已经进入POST的旧候选继续保留身份、预占及撤销处理。
- 将旧TP单标为`CANCEL_REQUESTED`并派发DELETE。
- 为最新ask−tick的SL接替单申请本地预占，额度足够就派发POST。
- 不等待旧TP的DELETE ACK、完整订单页、交易页或全账户刷新之后才决定是否发接替单。

第一版最多保留一笔待撤旧单和一笔接替单。若两笔都尚未解决，新的盘口变化更新同一个最新SL目标，并立即撤销已落后的接替单；不能每个tick再创建一笔第三单。

每个episode只有一个SL执行者。重复的SL信号、T180事件、行情回调合并到最新目标，不重复创建相同订单。

## 5. SL内部追价

保持现有规则：旧价≤当前ask−2tick时，触发按当前ask−tick追价。

- 行情事件到达后，先做本地追价/撤单判断，不先等待`reconcile_owned_order`完成。
- 先派发撤旧单；额度允许且执行槽位可用时，同时发接替单。
- 一个目标版本最多创建一次POST；新行情覆盖旧的未发送目标，已发送请求不伪装成已取消。
- 发单前最后一次本地校验价格/tick/预算；盘口变化则立即重算本地候选，不插入REST核对。
- 没有新行情、没有回执且没有订单变化时，不因重复轮询而持续撤挂。

SL不可回到HD/TP，等待期间价格改善也不撤销SL意图；只有原有配平、小敞口或截止规则能结束新修复操作。

## 6. 资金与敞口的本地预占

### 6.1 不把待撤单当成已撤

对每个已知签名订单ID分别记录：

- 已证明的经济成交数量与成本；
- 已观察到、尚未得到经济证明的成交；
- 尚可能成交的数量上界；
- POST、CANCEL以及终态证据的版本和先后顺序。

POSTING、ACK后活动、CANCEL_REQUESTED、UNKNOWN的可能成交量均保留预占。相同成交/订单身份只计一次；成交从未决转为实际时，同步减少其未决上界，不能在实际仓位和在途预占里重复计算。

### 6.2 session Delta区间

令：

- `D`：已证明的session实际YES数量减NO数量。
- `U_Y`：所有未决YES订单尚可能增加的数量上界，含未证明成交。
- `U_N`：所有未决NO订单尚可能增加的数量上界，含未证明成交。

则本地保守区间为：

```text
Delta_possible = [D - U_N, D + U_Y]
```

加入新单后检查整个区间。实际D处于限额内时，要求区间均在[-5,+5]内。

新YES单的数量上限为`5-D-U_Y`；新NO单为`5+D-U_N`。再结合目标实际缺口、现有最小股数、最小金额、资金和最大单量取合法数量。原有单个候选应减少实际绝对Delta的条件保留；额度只能容纳不足交易所最小数量时，不向上硬凑，先发撤单。

实际D已超限时，不能要求“不成交场景”立即回到5以内。沿用既有恢复规则：只允许减少实际超限的方向，新增订单不得扩大已有最坏风险边界；有可行数量才发恢复单。

### 6.3 资金

令`B0`为开场已有官方依据的session可用资金上界与15 USDC的较小值。

```text
已证明实际买入成本
  + 全部旧单尚可能花费的预占
  + 新单最大买入成本
  ≤ B0
```

本session的既有买入支出持续计入，不能按episode重置。未决成交与未决余量合计最多覆盖订单剩余成本一次；不预支尚未核实的退款或尾仓结算。

账户同步仍会校正和收紧B0及预占；已知余额异常、外部订单或仓位冲突触发立即撤风险单与异常隔离。无冲突的正常动作不等待账户页面因每次DELETE重新完成。

## 7. 并发撤挂的明确代价

本方案建议允许在硬限额内的有限重叠。其新增代价是旧单和接替单可能都成交，产生反向尾仓。并发组不保证双成交结果仍严格减少绝对Delta，即使两笔各自按实际缺口设计。

例：

```text
实际持有YES 5@0.30：D=+5
旧TP：NO 5@0.65，尚未证实撤销
新SL：NO 5@0.71

仅旧单成交：Delta=0
仅新单成交：Delta=0
两单都成交：Delta=-5，留下NO 5
资金最坏占用：1.50+3.25+3.55=8.30 USDC
```

这个并发组满足Delta≤5与15 USDC，但“双成交后留下NO5”是实际风险，不能描述成零代价加速。额外买入还会改变成本结构和最坏亏损，Delta上限并不保证亏损金额不变。

处理规则：任一成交事件到来，立即撤销不再需要的余单；按真实事实记账。小尾仓继续用≤2.5不修复规则；并发导致的反向尾仓沿用现有原始方向/反向尾仓保护，不为追求归零自动开启反复买回的循环。不得偷偷恢复NORMAL。

另一例：实际D=+3，旧NO尚可能成交5，再发NO5会使区间下界到-7，禁止。此时马上发撤单；新单等本地预占释放事件即可派发，不等整账户刷新。如果只允许无反向可能的执行，则常见5股旧单+5股新单也必须串行，这是一种不同取舍。

**开发前需要确认的新增执行语义：是否接受上述受Delta和资金限额约束的双成交/反向尾仓可能。本方案按接受有限重叠起草；不把该取舍当成已经获得实盘授权。**

## 8. 回执、成交和异常如何驱动动作

| 事件 | 立即动作 | 后台处理及预占 |
|---|---|---|
| POST ACK | 跟踪该订单；依据当前目标保留或立即请求撤销 | 不因ACK释放风险预占 |
| 本地明确未进入POST的候选作废 | 释放这笔未提交候选的预占，处理最新目标 | 已进入POST而响应不明的请求不适用 |
| 明确、可唯一绑定本次提交的拒单 | 释放该次未接受部分预占；用最新盘口继续尝试 | 同一已拒行情版本不热循环重发，等待新盘口或异常重试唤醒 |
| 超时、普通UNKNOWN、not found、身份不清的错误 | 保留全部可能接受的预占；按已知签名ID请求撤销 | 按ID查询订单/成交并异步处理；不把错误直接当未接受 |
| POST结束之后的明确已撤销ACK | 停止对该订单的周期性重复DELETE | 不能单凭ACK认定之前没有成交；未知已成交数量仍预占 |
| POST仍在途时的取消回执 | 保留原POST及其全部预占 | POST随后结束若可能迟到接受，重新派发取消；旧ACK不能覆盖晚接受 |
| 身份及数量均匹配的可靠订单终态 | 释放已证明不再可能成交的余量，唤醒额度受限的新操作 | 已报告但未证明的成交量继续预占，无需等待整账户positions页面 |
| 新MATCHED / 部分成交 / 迟到成交 | 立即保守撤销可能多买的余单，更新未决数量区间并重算目标 | 不直接写入已证明经济库存；同一身份去重，后续CONFIRMED或实际仓位及抵押品证明接续 |
| 已证明成交 | 更新实际库存和成本，并转移相应预占 | 经济事实仅计一次；状态名变化而数量不变不应重复触发新单 |
| 实际敞口≤2.5 | 停止新修复POST，立即请求撤余单 | 继续处理晚到事实，不清零库存/成本 |
| FAILED、身份冲突、账户真实矛盾 | 立即撤风险订单，隔离受影响的新BUY | 走现有完整事实核对；不以超时强行恢复 |
| 行情重连或tick变化 | 撤销失效订单，丢弃旧候选 | 重新建立本地有效行情/约束后继续；保持SL意图 |

未决POST最多保留一个接替目标。重试使用新命令版本与明确的签名ID，不能丢失旧命令身份，也不能重复计入或释放资金。

## 9. 截止、完成和恢复

- T240为硬截止：阻止所有尚未真正进入POST的候选；立即取消所有已知可能被接受的ID，包括POST仍在途的候选。
- 截止后收到的ACK、MATCHED、终态和迟到成交照常处理。不得用旧取消ACK掩盖迟到接受。
- Merge及重新进入NORMAL继续要求相应的订单/成交事实已得到安全核对；本方案取消的是每次SL动作之前的全session串行屏障，不取消最终账本结算与会话交接。
- 进程崩溃后仍沿用已知ID清理、禁止同市场自动续开仓的恢复模式；不在本次顺带实现自动接管交易。

## 10. 代码落地结构

### 独立SL执行者

按session建立单一SL执行者，串行消费信号、盘口、执行回执与成交事件；网络POST和DELETE任务可以并行。持有本地账本锁的范围仅覆盖目标合并与预占，不能覆盖整段网络请求或订单生命周期。

### 逐订单执行上下文

现有`BatchLifecycle.busy`、全session`safe_to_continue`和网络“已有批次在途”的标记，不再充当SL动作的全局串行锁。

`client.attempt/batch_attempts/network_batch_id/submit_guard/on_post_start`等共享可变字段必须改为逐命令上下文或隔离的SDK调用实例，确保并发DELETE/POST、迟到回执不会串到其他订单。先消除这些共享状态，不能只启动两个任务就宣称并发安全。

### 预占及事实分层

经济事实版本、订单执行版本与行情版本分别推进。CONFIRMED状态更新但已证明经济数量不变时，不撤销无关活动SL单或重复预占。所有实际/未决敞口都进入同一session账本，包含原始NORMAL余单和跨episode遗留事实。

### 后台同步

复用现有缓存采集作为对账源，但分离“观察到写发生”和“禁止所有执行直到全账户覆盖该写”的含义。定向订单/交易查询由异常和事实缺口驱动，不把每次POST/DELETE自动升级成下一次SL动作的全账户准入等待。

保持NORMAL和TP的既有准入要求；SL接替可以绕过等待旧TP整个生命周期返回的调用结构。外层runner仍按最终安全事实决定何时开始下一轮NORMAL。

## 11. 观测与验收

### 每个SL意图必须记录

实际信号识别、命令入队、预占完成、真实POST/DELETE开始、ACK、MATCHED、终态、CONFIRMED的单调时钟；同时记录episode、意图版本、签名ID、盘口版本、价量、实际Delta、可能Delta区间及资金预占。

历史路径触发时刻另列，不能当成当时已实际派发的信号。日志里必须分清`WAIT_LOCAL_RISK_CAPACITY`与账户后台同步进度，不能把未发单显示成已执行。

### 第一版工程目标

- 本地盘口/数量可用且预占允许时，SL识别至真实POST/DELETE发起的p95目标≤50ms。该目标待测试，不是现有达标声明；不含网络ACK和Maker成交时间。
- 正常快路径不等待前台REST、全账户快照、新的网络探测或固定2秒复核。
- TP→SL与SL→SL撤换均应覆盖并行派发，不能等旧单终态才调用新单POST。
- 每次资金及Delta预占均由同一session原子登记，包含所有未决组合；不能因重复事件生成第三笔可能成交的新单。
- 明确、有效的取消回执后不再周期性重复DELETE；POST晚接受、重开或事实冲突可以恢复取消。

### 必须覆盖的测试

1. 正常HD→SL，TP→SL，SL连续追价以及重复信号合并。
2. 旧、新单任意顺序部分/全部成交，两单都成交；验证资金、Delta区间与反向尾仓处理。
3. CANCEL先返回，POST后被接受；ACK丢失但实际已接受；UNKNOWN迟到成交。
4. 取消请求后才收到成交（24场15:05反例）；不得把not found或空交易页单独当零成交。
5. 订单终态先到、成交后到；未证明成交与实际证明接续且不重复计算。
6. MATCHED一直不转CONFIRMED，通过原有实际仓位/抵押品证据处理；FAILED及回滚不伪造经济事实。
7. 最小订单、最小金额导致本地预占不足；立即撤旧单，不突破限额凑单。
8. 实际超5恢复、≤2.5停修、<0.1配平、未决订单阻止重启NORMAL。
9. T180及T240事件和并发POST/DELETE竞态、截止后迟到接受、Merge交接。
10. 并发SDK请求身份隔离、日志故障、网络失败、重连、旧候选失效及崩溃清理。

24场日志用于复现旧流程事件和价格变化，注入竞态验证工程约束；不假定提前挂出的Maker必成交，不以回放虚构改善后的实盘PnL。
