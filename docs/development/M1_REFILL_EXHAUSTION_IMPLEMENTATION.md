## 实现行为

- 模式标识 m1_v1，复用现有 rdp-sm-run 入口、SessionFeed、BatchLifecycle、SMWindowExecutor、Gateway、成交账本与 T240 Merge。
- 新增 M1Engine/M1Controller、AP/RF/EX 因果检测和机会管理；旧 NORMAL/REPAIR 不参与该模式的库存决策。
- YES、NO 独立检测 RF_BID + EX_SELL。价格只定位队列、匹配成交、换算数量与支付金额，不参与选边、收益判断或开仓触发。
- 机会与活动挂单按其自身 token 检查盘口新鲜度；另一个 token 暂时安静不会成为隐含的方向否决条件。公共接收队列仍必须追上已知输入。
- 每笔目标预算 5 美金，按原始 RF Bid 档位向下取整数量。原生签名支付金额不得超过 5 美金；原旧策略 15 shares 上限不用于 M1。
- 累计买入支出和所有未决/未成交占款合计不超过 20 美金。双边库存不抵扣金额，部分成交关闭后不自动补足预算。
- 仅在 [T100,T240) 新提交 BUY。整个 session 最多一张活动挂单，关闭及成交核对完成后才处理下一机会。
- 每次新 RF 三轮及新 AP→EX 最多一次原生提交；UNKNOWN、明确拒绝和实际成交都不授权重复发送同一机会。未进入原生 POST 的准备失败不伪造一次提交。
- 订单截止是 RF、EX 和 T240 截止中的最早者，不因准备、网络、轮询或等待延长，不转 Taker、不追价。
- T240 起沿用现有撤单/核对及 Merge。已确认配对份数合并，真实残仓等待结算，Merge 回款不恢复买入。

## 入口与配置

独立配置在 config-m1/config.toml。没有修改原 config/、livecfg/ 的交易配置。

从仓库根目录运行：

    uv run polymaker rdp-sm-run --config-dir config-m1

该命令会连接实际账户并在条件成立时提交真实订单；这里提供入口，没有代用户执行实盘。

保留现有环境凭据和账户身份读取方式。该配置沿用原 config/config.toml 的 signature_type=2；没有创建、替换或展示凭据。原有单账户执行锁及未解决订单的启动核对照常生效。

执行一次命令只运行当前一个 BTC 5 分钟市场，没有添加自动跨场循环。

可在 T100 前启动以预热和积累独立轮次。晚启动只观察实际收到的剩余时段，不回放已经错过的机会。

## 检测和执行证据

- 复用现有有界异步 CAWriter 作为公共事件 sink，避免另建通用写盘框架。
- 原始公共帧及逐子事件的接收/处理时间、frame/row/change 索引、接受/拒绝原因、AP/RF/EX 事实写入 research_outputs/m1/<session-hash>/events.jsonl。
- 必需交易事实仍使用原有持久化 RiskJournal，记录准备、原生提交、订单 ID、成交、资金和 Merge；不以公共研究日志替代风险账本。
- RunResult 增加 m1_windows 和 m1_observation，包含信号计数、失败原因、最后候选与公共 writer 状态；面板支持 M1 阶段和订单归类。
- 自有订单活动期间不从污染的深度建立新 RF/AP/EX 机会。当前挂单使用原先冻结的证据、原截止时间、数据/档位检查和可见卖压恢复反证。关闭核对后从新的独立证据重新积累。
- AP/EX 及轮次封口必须等待接收队列中相应窗口的事件处理完毕。积压超出原处理期限记不可用，不回填确认。已知尚未处理的公共帧也阻止新提交。
- 公共队列/记录失败、乱序歧义、重复成交歧义、成交与盘口无法对齐、数据中断和 anchor 变化不会被当作零成交或成功承接。

## 执行预算

旧 BA 准入的 750ms POST floor + 500ms 最短挂单存活不适用于 M1；该模式使用独立金额与时间准入。

启动参考来自已有实际写操作记录：research_outputs/analysis/after2130_20261031/live-write-traces.json 中一笔 POST 为 307.334ms，三笔 DELETE 最大 1268.389ms。首版配置采用 400ms POST floor、50ms 最少剩余挂单存活，以及 1500ms 的近期 DELETE 上限。它们是有历史依据的启动预算，不是当前延迟的保证或充分的尾部统计。

近期真实 POST 耗时会抬高准入预算；公开 GET 不降低 POST floor。真实剩余信号寿命不足就跳过，未观察到当前 POST 时在日志中明确标记使用历史启动预算。下一次实盘可以直接检验此预算及有效机会覆盖。

本地到期会发起撤单，但无法保证交易所不会在撤单完成前继续撮合。迟到、部分和 UNKNOWN 成交全部保留并走原关闭证明，不通过删样本让结果变好。

## 定时运行状态

M1 复用现有 50ms 时间边界任务，每 10 秒写入 `sm_m1_heartbeat`，阶段变化时立即写入。
默认终端日志同步展示阶段、市场 T 时间、行情连接和更新数量、双边盘口可用性、待处理帧、
AP/RF/EX 累计确认次数、新增不可用事件、当前等待及信号失效原因、提交数、确认成交数、
双边库存和累计支出加占款。等待 T100、等待信号、异步读取、关闭订单及等待结算期间均有状态输出。
`DATA_UNAVAILABLE` 与 `BLOCKED` 明确区分数据不可用、阻塞与普通观察，不以进程存活推断交易就绪。

状态采集只读已有内存，不请求交易所、不推进信号、不授权交易。终端写入复用后台日志线程；
定时器只提前投递状态事件，订单结果仍由原协调器在关闭核对后展示，防止重复计数。
高频交替等待原因保留在明细日志，通过定时状态汇总展示，避免刷屏。`--json-only` 不输出终端状态，
仍保存 journal 定时事件并保留 stdout 的单份最终 JSON。运行中的进程在下次启动时加载此修改。
