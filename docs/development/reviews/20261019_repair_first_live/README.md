## 根因与证据

`SyncObserver.position_proof_signature`包含该订单、相关成交、账户资金及仓位。新的成交改变资金/仓位，旧证明失效。原实现每个周期都把失效订单重新加入`pending`，初始调度优先级为0，却继续保留失效的签名。

每轮最多读取4个订单详情。旧订单核对后被移除；下一轮旧签名依旧失效，又被优先级0插回。已经排队等待重读的新订单获得过正的序号，持续被这些重新插队的旧订单挡住。

## 修复与复现

修复仅改`SyncObserver._orders_round`的失效证明处理：排入一次重新核对后，删除该旧签名；在锁内比较签名，避免并发时覆盖执行器刚提交的新证明。后续该订单按正常队列序号轮转。每轮4个详情的上限、周期、资金预算、实际仓位证明及关闭屏障继续有效。策略阈值与HD/TP/SL规则保持原值。

新增[test_repair_live_cache_regression.py](../../../../tests/test_repair_live_cache_regression.py)：

1. 确定性调度复现：4个旧失效证明占满第一轮，下一轮必须读到排序更靠后的新订单，不能永久反复读取旧单。
2. 实际缓存执行：积累4个无成交旧订单后，开仓MATCHED、REPAIR成交MINED，以实际仓位配平，再次NORMAL实际成交；使用真实控制器、SDK、WAL、缓存与核对，外部交易所为模拟。

用移除本次修复块的旧方法重跑上述最终测试，两项均失败：新详情缺失，以及`SYNC_CACHE_NOT_READY`关闭屏障阻塞。该旧方法仅在单独的测试进程中替换，工作目录生产源码没有回退。恢复修复后重新验证；最终结果见[validation.json](validation.json)。

修复后全量回归2002项通过、2项跳过；最终缓存/执行专项62项通过。全量收集后仅加强测试夹具的旧订单积累数量，最终专项覆盖加强后的版本；生产代码在回归期间没有改变。两套本地REPAIR就绪检查均返回0，配置仅把验证引用更新到本次修复记录。

本次实盘还暴露出TP预热表现：早先在浮盈路径上锁存TP，首次报价因sigma未知而等待；能报价时浮盈已变负，NO@0.57若成交将与YES@0.44锁定−0.05 USDC。实际该TP没有成交，随后按路径规则转SL。此为现有“状态锁存＋首次按当时盘口定价”的行为，本次缓存修复不改变TP语义，也不以本场结果直接调整阈值。

修复不会追补已经结束市场的订单，也不启动真实交易进程。下一次启动使用修复后的缓存调度。进程崩溃后的自动交易续跑和整体正EV验证仍不在本次工程修复完成范围内。
