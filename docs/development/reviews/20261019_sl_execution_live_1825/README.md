## 问题一：单订单解析失败使网络恢复条件无法满足

证据链已闭合：

1. 第五单原生 POST T111.884578 开始，T112.017412 已独立发 DELETE，T112.397278 收到 POST 返回：`order <本单签名ID> is invalid. Already canceled.`。这是确实发生的并发撤挂竞态，不是没有发单。
2. 该 ID 的后台详情HTTP为200，但 `order_row` 无法得到合法订单，`ReadEvidence` 为 `ValueError / SYNC_ORDER_INVALID / http_status=null`。原始响应体未保留，不能进一步断言一定是JSON null或哪种具体格式。
3. `rdp_sm_sync.py:442`仅把详情HTTP404单列为不影响整组健康。此处HTTP200解析失败仍把整个orders round记为失败，`_periodic`继而退避2、4、8秒。
4. `/time`和订单详情在同一个orders round内，健康探测也被拖到约8.44秒一次。T128–240共13次`/time`，多数HTTP约0.2秒且成功；不是服务器一直不可达。
5. `rdp_sm_network.py:151`要求最近3个快探测均在5秒内，最新不超过2秒。约8.4秒一次的探测不能满足这个条件。PAUSED因而持续到T256.664，超过REPAIR的T240截止。
6. 主循环在进入REPAIR之前检查网络许可，网络恢复失败时不会重新调用SL控制器。T180强制SL也不会绕过真实网络许可，因此本场后段没有继续POST。

离线用同一 `NetworkHealth` 类复现：8.4秒探测间隔始终PAUSED；同样的成功响应改为0.5秒间隔可以进入PROBE。复现没有发起HTTP，也没有改变生产熔断参数。

修复方向应是隔离“这个订单事实尚不明确”和“整个网络是否恢复”，使单订单错误的退避不饿死健康时钟和其他正常集合读取；保留原网络冷却与恢复门槛。未知订单仍保留风险，不能把404或HTTP200解析失败直接视作零成交、提前释放。

## 问题二：SL内部没有及时消费已有的已撤提交证明分支

本次第五单在SL actor内收到UNKNOWN后继续逐单DELETE/等待普通终态；它没有在此阶段接入已有的、签名ID严格匹配的`_verify_canceled_submission`证明路径。该单在SL actor内收到29次DELETE，最终关闭再做1次，共30次。直到actor等待事实超时、进入最终全量核对，才使用已有分支确认REJECTED，结束本窗口。

后台 `_detail_requirements` 随后仍保留这个无法解析有效详情的签名ID：整场有25次 `SYNC_ORDER_INVALID`，一直到T298.526。即使主执行已判定该提交未被接受，这个后台工作仍持续拖慢orders lane。这是与问题一相互放大的生命周期遗漏。

新一轮更高追价在资金/Delta不够时立即撤旧单，是已确认的硬限额优先行为。本场账户初始资金实际只有15.538566 USDC，20是session上限，不是可花余额；三张各5股NO若同时未决还会突破Delta区间。不能靠无条件放开第三单解决。需要补齐的是已撤回执的及时、严格证明和对应后台任务退役，避免一个正常可能发生的撤挂竞态演变成整场不可修复。

## 问题三：阻塞日志误导

`rdp_sm_sl.py:463–470`把所有不能提交、且非资金不足的原因归为 `WAIT_DELTA_CAPACITY`。实际上 `allowed` 还检查网络、盘口代次、时间、FAILED隔离等。因此T115.161的日志不能据此判定Delta确实无空间。

当时已花5.80，旧单仅NO5@0.90仍预占4.50。示例再挂NO5@0.92，承诺14.90，小于实际资金15.538566；可能Delta区间从[0,+5]到[-5,+5]，账本允许。该示例不冒充当时缺失的精确盘口，但足以说明日志遗漏网络阻塞。应让准入返回明确原因，并为未发出的更高目标记录目标版本与价量，才能准确还原每次为何撤掉仍在POST的订单。
