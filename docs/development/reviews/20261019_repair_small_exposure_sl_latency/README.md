# 小敞口停止修复与 SL 分段耗时

2026-10-19。按用户意见实现小敞口规则，同时对上一批 12 场中的全部 10 轮 SL、21 个实际 SL 订单窗口展开分析。本次未启动交易进程或发送真实订单；运行中的旧 Python 进程不会热加载这些改动。

## 已实现的小敞口规则

当前 `delta_limit=5` 保持不变，HD/TP/SL 控制器以整个 session 的实际经济仓位计算 `Delta=YES−NO`。

1. **`|Delta|≤2.5` 股不发新 REPAIR 单。** 包括恰好 2.5 股：若最低买 5 股，全额成交只会把 +2.5 变为 −2.5，并未降低绝对敞口。
2. 已在场的修复单部分成交后，若可核实的真实 Delta 降到该区间，则撤余单；所有未解成交和迟到成交仍走原有核对屏障。不在存在未解 pending 成交时据未经证明的数量宣布完成。
3. **每张新修复单均要求整单成交后 `|Delta_after|<|Delta_before|`。** 固定 2.5 门槛只覆盖最低 5 股；低价格下 $1 最小金额可要求 10 股甚至更多，必须同时避免等量或更大的反向敞口。
4. 不把 2.5 股当 dust，不清零仓位或成本，不放宽 Data API 的 0.01 股容差，不宣告配平。原 episode 继续拥有 session，不因这个门槛重新开启 NORMAL；保留真实剩余仓位，等待后续可核实成交变化或 T240 后的 Merge/最终结算。
5. Delta 后续因迟到成交变化时重新评估；若重新高于门槛，仍可按原有已锁存 TP/SL 状态修复。小敞口等待按 opening_window + 实际 Delta 去重记日志，避免重复刷同一状态。

日志新增 `sm_repair_small_exposure`，人类日志显示 `WAIT_WITH_RESIDUAL`，并明确保留实际仓位与成本。新单计划和最终提交守卫都检查敞口下降，避免仅在生成信号时检查。

对上一批事实的影响只作准入解释，不作反事实收益预测：

- 12:20 的 NO 0.676664 股开仓会进入保留残仓，不再为了它新增 YES 5 股。
- 12:30 的 YES 5 股若以 NO 10@0.10 修复，Delta 从 +5 变为 −5，新严格下降检查会拒绝这张单；5 股初始敞口仍然保留，之后是否有可行报价需按新行情复核。
- 12:40 的 NO 0.565714 股尾仓不再继续修复；本次规则本身不阻止此前 4.994286 股缺口以 5.56 股修复，因为绝对敞口确实降到了 0.565714。
- 本次不声称 Maker 订单在每一个部分成交时刻都单调减小绝对 Delta。若最低订单跨过零，可能先配平再形成较小反向尾仓；本规则约束计划的整单结果，并在观察到小敞口时尝试撤余单，仍存在成交观察与取消延迟。

### 为什么每次重挂前要2–3秒

已经核实的代码和日志链条：

1. `review_active()` 已把 TP→SL 的撤单判断放在 REST 对账之前，但 **SL 内的追价判断仍排在 `await reconcile_owned_order()` 之后**。缓存读取需满足写后时间边界，因此价格已恶化时，可能先等待订单、成交缓存，才提出撤单。
2. `BatchLifecycle` 的 watcher 和主流程关闭核对均可发 DELETE；w11 首次两次 DELETE 几乎同时开始。之后 watcher 在权威订单详情显示终态前继续重试，总计4/4/3次。
3. 每个完成的 DELETE 都推进 `CachedExecutionReads.last_write`，关闭证明要求 time/open_orders/trades/capital/positions 的读取起点晚于最后写入。新鲜订单读数不能替代2秒一次的账户读数。
4. w11 第一次 DELETE T73.857 返回，最后一次 T74.772 返回，T75.613 才取得完整关闭快照；w12 最后一次 DELETE T77.761，T79.451 左右才得到包含写后账户读数的完整快照。w13 类似。

所以观测到的7.612秒主要是完整证明与轮询等待、重复取消推进写后边界；并非单次HTTP慢。不能单凭时间线声称每个重复DELETE都能节省相等时间，也没有据此模拟更早成交或收益。

## 优化顺序（本次尚未修改执行机制或信号参数）

1. **SL追价取消不等待REST。** 在新鲜有效盘口、SL已锁存、旧价已落后至少既定2tick时，先请求取消；保持原有全量关闭屏障，查清迟到成交后才重挂，不提前推算可下数量。
2. **共享一次在途取消，并对明确取消成功停止冗余重试。** POST已结束、精确签名ID收到明确取消成功时可停止重复DELETE，仍保留全部风险预留直到订单/成交/账户完整证明通过；UNKNOWN、取消失败或迟到LIVE矛盾恢复原有取消。需要测试POST未结束、成交与取消交叉、部分成功批次和迟到活动订单。
3. **REPAIR关键阶段的缓存调度优先级。** 仍由唯一同步服务发读请求，不让执行器自行刷新；优先当前订单的终态详情，评估在SL撤换期间短时提高账户采集频率，以减少正常2秒轮询造成的空档。此项需量化API请求预算与上游限流，不能只改睡眠或超时。
4. **将信号观察和写入准入分开。** 在等待关闭/账户核对时持续观察并锁存风险意图，日志分别记条件发生、检测、允许下单、POST、ACK、观察成交。不会凭此越过成交/账户证明，单独做此项未必能消除最差场的7.98秒。
5. **处理已CONFIRMED但Data API副本迟到。** 如果要缩短这道等待，应引入可验证的同账户、同token链上/权威仓位及资金证明，与已确认成交精确对账；不能将5股差异当dust、扩大0.01容差或用等待超时替代证据。本次保持现有约束，尚未实现新的证明来源。

优先处理可量化的执行空档，再评估是否需要调信号阈值。提高Maker成交率仍需真实队列/成交数据验证；本报告不承诺消除所有Maker等待或得到正EV。
