# 新信号的数据能力说明

记录日期：2026-11-11。用途是SOP交接，不是行情质量或模拟器的验收报告。本次只读了字段与源码，没有扫描录制、运行测试或改动适配器。

## 已核对的接口事实

官方公开流区分订单簿与成交消息。book和price_change给出价档数量；last_trade_price给出成交方向与价格等字段。统一SDK文档允许部分成交size、timestamp、transactionHash缺失，不能因接口存在就假定每条数据齐全。[官方Market Channel](https://docs.polymarket.com/api-reference/wss/market)，[官方Real-Time Data](https://docs.polymarket.com/market-data/realtime-data)

这些文档本次查看的字段中没有给出book与trade逐笔共同撮合序号；故不能仅以两个消息时间接近，证明它们是一次成交前后的精确库存。这是对所读接口的能力边界判断，不宣称所有平台数据接口都缺这项能力。

## 工作区中的四个交接陷阱

| 项目 | 读到的实现 | 对新SOP的影响 |
|---|---|---|
| 直接成交与镜像 | `feed.py::_trade` 先生成直接/互补视图，按经济视图身份去重；先来的镜像可占用后来的直接视图身份 | 新版要求直接流时，不能仅从已去重的NORMALIZED_TRADE筛选mirrored=false；需原始来源或等价来源集合 |
| 时间基准 | `Round.qualified_at`取context.now；hold_start使用received；关闭摘要导出qualified_available_at | M16不能直接相减，需要同接收时钟的完整事件路径和最终保持段 |
| 深度数量 | `feed.py::_depth`把price_change.size作为该价新的总量赋值 | 不能把它累计成“新增挂量”；只有前后差才是可见净变化，仍不能分开逐单挂入/撤出 |
| 锚档数量来源 | `Book.received/source`被全书更新及一致的BBO刷新；_depth也会在其他档变化时调用observer.depth | 全书新鲜度及回调时刻不能充当P数量事件时刻；M16跨越端点、M17前置数量和成交后复核都要原档事件身份 |

源码：[feed.py](../../research/maker_signals/feed.py)、[primitives.py](../../research/maker_signals/primitives.py)、[model.py](../../research/maker_signals/model.py)。目录中保留的源码hash只标识阅读版本，不证明任何正在运行的服务已加载该版本。

19:57复核primitives.py：Rounds新增可配置stable_recovery，默认0.50，保持/撤销仍用其0.8/0.4倍的滞回比例。该参数不能直接证明新COMMON的严格保持；M18索引记录这次阅读hash，早先信号的来源hash仍保留原阅读版本。本任务没有修改该源码。

镜像去重例（解释代码行为，不是数据测试）：如果某token的SELL经济视图先由互补token的BUY生成，后来的直接SELL按相同交易/时间/数量身份可能被忽略。去掉mirrored=true后，早先那个视图也被删掉，结果会漏掉直接流。必须在来源信息尚未丢失的阶段定义“仅直接成交”。

锚档来源例（规则说明）：P在100ms最后一次明确报出低数量，240ms只有Ask变化，270ms才出现P恢复事件。把240ms的observer回调当成P再次报量，会把实际170ms的观测间隔写成30ms，错误通过M16的50ms边界要求。v1.1须使用携带P数量的事件；BBO刷新也不能替代它。普通健康流中的完整快照可以提供P数量；断线/缺口后的重建快照先终止旧generation，不能跨重建复核旧root。

## 新SOP所需能力

互补盘口另见[重复归因审查](COMPLEMENT_PROVENANCE.md)：本地镜像、不同token原始消息和链上填单腿不能直接当成独立证据。已读官方合约支持多maker撮合；transaction_hash不是逐经济成交身份。当前公开字段尚未给出足以证明跨侧独立计量的合同，因此该方向暂不新增M编号，也不修改现有信号参数。

| 信号 | 必需的额外信息 | 只有旧轮摘要时 |
|---|---|---|
| M12/M14 | 两侧原档真实成交、逐次减损/恢复、严格末尾保持、冻结供给恢复界限 | 原hold滞回与新严格保持不同，不能直接复用stable |
| M13/M15 | 原LW固定集合、形成前500ms到整个root终点的累计BUY、全程guard、新受击资格键 | 不能只从3秒滚动缓存重算历史累计量；不得把自然TTL与硬失效混为一谈 |
| M16 | 同时钟受击时刻、最终低谷、最终连续保持段、明确携带P数量的跨越前后帧、时钟量化 | qualified_available_at与hold_start不足；全书更新回调也不能补造原档边界 |
| M17 | 原始直接SELL身份/量、前置P数量事件、各笔成交后更晚的同档数量、完整中间底线、跨发布阶段待复核集合 | H加末量不能证明已及时更新；不能跳过窗口结束到发布之间的新成交 |
| M18 | 两轮同档H/Q0/低谷/恢复路径、初量来源、每轮最后SELL之后且仍在窗口内的P数量事件 | 有H/L摘要也不足以证明严格稳定和末笔成交后的量；不要求M16时间区间或M17逐笔100ms复核 |
| M19 | 两轮同Ask的直接BUY、H/L/u/d/r及轮末来源；配对Bid严格稳定、数量来源和各自连续guard | H>=L仅为筛选，不是成交扣量归因；不能将回补后变薄都称为被吃掉，也不能用未来复核补早前确认 |
| M20 | 冻结P及其下方两实际Bid档的初量与全路径、P逐笔SELL复核、更低档实际SELL识别 | top1/RF摘要不够；动态前三档不能代替固定集合，三档总量不能代替各档条件，也不能识别同一订单搬家 |
| M21 v1.1 | 直接BUY存在性来源、原始批次/等价原子边界、两轮SELL及P/A前置/末端数量、250ms Ask平稳基线 | 过滤后空流和depth/BBO coverage均不足以证明零BUY；早接收晚处理BUY不是确认后新流量 |
| M22 | 旧Bid支撑及floor路径、固定三Ask初量/全路径、近档BUY及末端数量来源、更高档BUY存在性、原始批次边界 | 动态top3/RF摘要不足；各档独立过线不代表总量合格，新Ask结构不能替旧Bid续期 |
| M23 | 明确P净增前后量、直接SELL完整性、种子后首笔身份、原档初末量来源、双时钟、批次及Fpre/F路径 | RF摘要不能替代先加后卖；过滤后零SELL不可靠，先跌破再收到SELL不能追认较低底线 |

测试模块应分别标记 `SUPPORTED_BY_INPUT_CONTRACT`、`REQUIRES_RAW_RECONSTRUCTION`、`UNAVAILABLE`。这些是逐输入版本的能力标签，不能从SOP存在推导“已经支持”。未知事件顺序、缺失所需字段、镜像重复归因和不完整质量覆盖均应显式保留。

## 接收、可得与截止的交接

最新[交接审查](CAUSAL_HANDOFF_REVIEW.md)对应M12–M16 v1.2及M18 v1.1。新阶段不能只比输入序号，还须首笔received晚于参考/种子的available确认时刻；轮后guard则用received>=窗口终点筛选已处理到发布边界的事件。缺少任一时钟或完整交接路径时不能从当前快照补造“始终有效”。M17/M19/M20原有明确交接保持不变。

进一步来源核对见[成交时间结构说明](TRADE_TIMING_CAPABILITIES.md)。CausalCapture顶层monotonic_ns来自emit边界，原接收单调时间另存payload.received_monotonic_ns且可缺失；同一原始消息拆开的多行共用接收时间。已读service采集TRADE的payload未携带transaction_hash或原始帧身份，不能把本地event_seq当成经济成交ID。其他原始录制可能保留这些信息，须按输入版本核验，不能由字段schema推定实际已提供。

M16/M17的v1.1进一步区分“统计窗口结束”和“可以发出候选”。已关闭窗口到实际发布之间发生过的硬失效不能因当前又恢复而被删除。M17此段的新SELL虽不进入原H，也须进入复核监控，待复核集合不为空时禁止首次提交。

M17每笔的100ms预算为 `trade.received+100ms`，复核必须在该截止前已经available；到期等号失效。不能把接收时及时但处理时已晚到的更新追认为一直有效，也不能从确认或处理时刻重新给100ms。发送前允许等待复核，但原候选deadline与COMMON最短发送余量照常扣减；已发送订单中的未复核暴露及取消在途成交全部保留。这是可得信息下的执行规则，不是已验证的队列或收益模型。

M18只在轮关闭时要求数量事件已覆盖该轮全部计量成交，且该数量事件本身仍在原received窗口内；不延长500ms等未来复核。它与M17逐笔100ms复核的样本选择不同，不能借M17的通过率宣称M18已支持。两者都要求明确的锚档数量来源，而非全书更新时间。

M19对两轮Ask和配对Bid均要求前置/轮末数量来源，并在第二Ask/Bid窗口终点到可得确认之间检查冻结guard。它不要求识别同一笔回补被哪笔BUY消耗，也不把H>=L视为这种证明；若研究“反复回补被吃掉”，L2的净数量及全窗成交不足以唯一重建撤挂过程，该方向暂未单独编号。

M20使用固定三档的净变化及总量，前置来源须能追溯到首笔SELL之前；P成交后按100ms预算明确复核。后方无实际成交时，可在完整连续增量合同下延续其最后数量，不强求每次P成交都重发后方档；缺口仍UNKNOWN。中间子更新是否造成结构失效须按冻结的输入顺序保留，不能仅用最终合并book掩盖。

M21 v1.1见[零记录证据审查](ABSENCE_EVIDENCE_REVIEW.md)。读到的Feed在深度/BBO更新时写coverage，因此每桶有标记不单独证明本token的直接BUY完整。M21要求直接来源未丢失的存在性守卫、原始批次完成后发布；received早于或等于确认但后来才可得的root内BUY，在发现时结束，覆盖两轮间和关闭到发布之间。Service的部分解析跳过分支本身没有GAP事件，这只是所读源码能力边界，不证明实际运行发生丢失；没有原始来源合同不能宣称本版已支持。其他信号的覆盖规则本轮不重定义。

M20/M22的多档条件还依赖[深度批次语意](DEPTH_BATCH_SEMANTICS.md)：完整book是一份状态，price_change按本版冻结的原始顺序逐项检查，候选发布边界另行维护。已读旧Feed确实在各增量后调用中间guard、再批后发布；原生Service拆出的DELTA行不直接携带父消息/批次末行身份。输入顺序不是已证明的市场内部顺序，改为合并末态会改变样本，不能仍声称复现同一v1。当前仅补说明，不改任何信号参数或采集代码。

## 价格角色与计算边界

允许用价格确定同一档、Bid/Ask侧、tick合法性、post-only、数量预算和结果分层。来源核验不应悄悄引入价格推进或外部BTC价格来补方向。只有L2时不把净量留存称为同一订单/参与者留存，也不把公开成交总量直接当成策略订单成交量。

额外字段属于SOP交接要求，不要求本任务或测试模块复制一套逐tick日志。已有原始记录可用时，优先保存有限root范围的事件引用与聚合审计；能力缺失就明确缺失，不为凑齐字段启动本任务的新录制或扫描。
